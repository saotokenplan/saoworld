## 三、异常处理子流程

### 1. 无近周改动处理
- **触发条件**：`git log --since='7 days ago'` 无提交，或仅有与本周目标无关的文档/元数据扰动
- **处理流程**：
  1. 明确记录“本周无实质代码改动”
  2. 不实施业务代码重构
  3. 仅产出分析报告、治理建议、规范沉淀与项目状态同步

### 2. 风险不可确认处理
- **触发条件**：候选重构项缺少足够测试、存在跨模块连锁影响、依赖真实运行时环境
- **处理流程**：
  1. 将该项降级为“建议纳入下周”或“暂缓处理”
  2. 在报告中记录风险、影响范围和建议前置条件
  3. 不在本轮强行落地

### 3. Git 流程阻塞处理
- **触发条件**：工作区非预期脏、推送权限失败、分支切换/合并存在冲突
- **处理流程**：
  1. 先停止 destructive 或跨分支操作
  2. 记录阻塞原因
  3. 向用户说明无法安全继续的原因后再决策

## 四、风险点识别与预防

| 风险类型 | 风险描述 | 预防措施 |
|---------|---------|---------|
| 结论失真风险 | 近周无提交却仍然输出“本周改动分析” | 以 Git 历史为第一证据源，明确写出“无实质改动” |
| 过度重构风险 | 为了“更优雅”而进行大面积改写 | 只实施高价值低风险项，严格限制改动范围 |
| 测试缺口风险 | 缺乏针对性测试导致回归风险不可控 | 修改业务代码时同步补最小高价值测试 |
| 运行时依赖风险 | 真正验证依赖 PostgreSQL/Redis/Docker/Godot 导出环境 | 无环境时仅做静态/单测级验证，并在报告中披露 |
| Git 误操作风险 | 当前用户要求包含提交、合并、删分支等高影响动作 | 仅在用户确认规划后执行，且执行前再次检查仓库状态 |
