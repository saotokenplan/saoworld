# 周六产品管理任务规划

> 任务名称：每周产品管理工作（周六版）
> 执行日期：2026-08-22
> 统计窗口：2026-08-16 至 2026-08-22
> 当前分支：`feature-prd`
> 当前阶段：规划中，待用户确认后执行

## 1. 任务目标

围绕当前 Sprint 与产品战略完成一次周六复盘，基于最近 7 天的执行证据评估本周进度、偏差、风险与方向，并同步更新项目状态文档、生成周报；若当前迭代已接近完成，则提前规划后续迭代重点。若当天满足月度条件，则追加月报与战略对齐分析。

## 3. 六阶段执行方案

### 阶段 1：输入收集与时间窗口筛选

- 读取本周复盘所需的核心需求、战略、路线图、里程碑和项目状态文档
- 仅筛选最近 7 天内的执行摘要与每日进展文件
- 读取最近一份周报作为对比基线
- 判断当天是否为当月第一个周六，以决定是否追加月报
- 若任一关键输入缺失，统一标记为“待补充”，不编造结论

### 阶段 2：Sprint 状态与执行偏差分析

- 识别当前 Sprint 阶段、阶段目标、计划任务与实际推进状态
- 汇总本周已完成、进行中、未开始任务并估算占比
- 对比计划与实际，分析偏差来源：
  - 进度滞后
  - 范围蔓延
  - 优先级错位
  - 资源或依赖冲突
- 评估核心需求与里程碑达成度

### 阶段 3：迭代方向评估与纠偏判断

- 对照产品战略、路线图、Sprint 目标和本周实际进展
- 给出当前迭代方向评估：
  - `正常`
  - `需关注`
  - `偏离`
- 为结论提供证据，包括最近 7 天执行摘要、每日进展、当前状态文档和计划文档
- 若存在偏差，输出明确纠偏建议与优先级调整建议

### 阶段 4：后续迭代规划

- 评估当前迭代完成率是否达到接近完成阈值：
  - 总体完成率是否 `>= 85%`
  - 核心链路任务是否基本完成
- 若接近完成，则不等待原排期，直接规划下一周或下一迭代重点
- 后续规划必须明确：
  - 核心目标
  - 关键任务
  - 前置依赖
  - 验收信号
  - 风险收敛动作
- 规划原则为渐进式价值交付，优先保障主链路与关键闭环

### 阶段 5：文档同步与报告产出

- 更新 `docs/00-governance/project-status.md`，同步：
  - 当前阶段描述
  - 本周状态总结
  - 关键风险
  - 本周完成情况
  - 下周待办任务清单
  - 后续迭代方向
- 若 `docs/40-dev-loop/weekly-report-2026-08-22.md` 不存在，则新建周报
- 若周报已存在，则跳过生成，仅在最终总结中说明状态
- 若当天是当月第一个周六，则额外生成 `docs/40-dev-loop/monthly-report-2026-08-22.md`

### 阶段 6：校验、提交与分支处理

- 校验文档结论与证据是否一致，缺失信息是否都已标注“待补充”
- 检查新增或修改文档的结构与链接有效性
- 进行 Git 提交与推送，提交信息固定为：
  - `chore(product): 每周进展更新 - 2026-08-22`
- 处理分支操作前再次核实当前分支状态
- 当前已确认所在分支就是 `feature-prd`，因此用户要求中的：
  - “切换到 `feature-prd` 并拉取最新代码”
  - “将当前临时分支合并到 `feature-prd`”
  - “删除当前临时分支”
  与现状存在冲突；执行阶段将以实际 Git 状态为准，若不存在独立临时分支，则只能完成提交与推送，并在结果中明确说明该部分无法按字面执行
