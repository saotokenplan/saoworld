以“产品经理”角色完成本周产品管理闭环：收集最近 7 天项目输入，评估 Sprint 与里程碑进度，判断迭代方向是否偏离，必要时规划后续迭代，更新 `docs/00-governance/project-status.md`，并按条件生成本周周报与本月月报，同时执行可落地的 Git 提交、推送与分支合并流程。

## 3. 六阶段执行方案

### 阶段 1：输入收集与窗口筛选

- 读取战略、路线图、迭代计划、里程碑、核心需求、社区需求、项目状态文档
- 识别最近 7 天内的执行摘要与每日进展文件
- 读取最近一份已有周报作为对比基线
- 若发现缺失文档或统计窗口内无文件，明确标注“待补充”，不编造结论

### 阶段 2：本周执行状态分析

- 识别当前 Sprint 所处阶段、阶段目标、计划任务与实际完成情况
- 统计本周已完成、进行中、未开始任务及占比
- 评估 Sprint 进度偏差、核心需求完成率、里程碑达成情况
- 提炼关键成果、价值交付、阻塞问题、跨团队依赖和资源冲突

### 阶段 3：迭代方向评估与纠偏

- 对比产品战略、Sprint 目标和本周实际进展
- 判断当前迭代方向为“正常 / 需关注 / 偏离”
- 识别需求蔓延、优先级错位、关键任务滞后、价值交付不集中等问题
- 输出判断依据、纠偏建议与下周任务优先级调整建议

### 阶段 4：后续迭代规划判定

- 判断当前迭代完成率是否达到接近完成阈值（完成率 >= 85% 或核心链路任务已完成）
- 若接近完成，则提前规划下一周或下一迭代重点
- 后续规划需明确：核心目标、关键任务、前置依赖、验收信号
- 规划原则为渐进式价值交付，优先保障主链路、关键闭环和风险收敛

### 阶段 5：文档更新与报告生成

- 更新 `docs/00-governance/project-status.md`
- 检查 `docs/40-dev-loop/weekly-report-2026-09-12.md` 是否已存在
- 若不存在，则生成本周周报；若已存在，则跳过新建并仅补充简要状态说明
- 月报仅在“当月第一个周六”时执行，本次默认不进入该分支

### 阶段 6：交付与 Git 流程

- 汇总对用户的简要结论输出
- 检查工作区与当前分支状态
- 按用户要求执行：
  - `git add` / `git commit`
  - `git push`
  - 切换到 `feature-prd`
  - 将当前工作分支以 `--no-ff` 合并到 `feature-prd`
  - 删除当前临时分支（本地与远程）
- 若当前实际分支并非“可被合并的临时分支”，或删除/切换会造成风险，将先核实并在执行时据实说明

## 5. 风险控制原则

- 缺失输入文档时只输出“待补充”，不推断不存在的事实
- 周报和项目状态必须基于仓库内可追溯证据，不补造进度
- 若本日周报已存在，不重复覆盖内容，避免产生冲突版本
- Git 操作前先检查当前分支、未提交修改和远程状态，避免误删分支
- 若发现与本任务无关的异常工作区改动，立即暂停并请求人工决策
