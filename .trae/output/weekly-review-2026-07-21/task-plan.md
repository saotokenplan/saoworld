## 3. 六阶段执行方案

### 阶段 1：输入收集与边界确认

- 汇总最近 7 天提交记录、变更目录、核心文件和主要主题
- 读取与热点模块直接相关的规范文档
- 判断本轮是否存在“无实质代码改动”的分支条件
- 输出可证据化的周变更清单

### 阶段 2：改动主题识别

- 按模块归类本周改动：功能开发、缺陷修复、测试补强、工具链、文档治理
- 判断热点是否集中于 API 层、Repository 层、领域模型、异步任务、客户端脚本、测试基建
- 形成本周改动概览、风险区域和结构性问题候选

### 阶段 3：多维度深度分析

- 从架构一致性、可读性、可靠性、稳定性、可测试性、可维护性 6 个维度分析
- 对每个问题记录：证据文件、影响范围、严重程度、建议动作
- 将问题归类为：
  - 立即实施
  - 建议纳入下周
  - 暂缓处理

### 阶段 4：立即实施项设计

- 仅筛选高价值、低风险、可回滚的优化项
- 优先处理：
  - 重复逻辑抽取
  - 明显越层/职责混乱
  - 潜在稳定性缺陷
  - 高回归风险测试缺口
- 为每个候选修改点确认：
  - 不偏离当前需求目标
  - 可用现有测试或新增最小测试验证
  - 回滚路径清晰

### 阶段 5：执行重构与验证

- 在用户确认后，按小步方式实施“立即实施”项
- 若修改 `services/` 或 `workers/`，同步更新对应测试
- 运行与改动直接相关的 `ruff`、`mypy`、`pytest`
- 仅在验证通过或风险可控时保留改动

### 阶段 6：沉淀与交付

- 生成或更新：
  - `docs/40-dev-loop/weekly-code-review/weekly-code-review-2026-07-21.md`
  - `docs/00-governance/project-status.md`
- 提炼规范或 skills 草案，沉淀可复用检查项
- 若最终执行了代码修改，再按 Git 规范提交与推送

## 5. 风险控制原则

- 不做无边界重写
- 不因“代码风格更优雅”而改变既有行为
- 任何无法快速验证安全性的候选改动，降级为治理建议，不直接落地
- 如果发现环境依赖不足，优先执行静态分析、单测和可本地完成的回归检查
- 若执行过程中发现与当前工作无关的异常变更，立即暂停并请求人工决策
