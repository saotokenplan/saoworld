## 1. 任务目标

在最近 7 天代码改动的基础上，完成可追溯的周度代码分析，识别高价值、低风险、可验证的治理点，并仅在风险可控前提下实施小步重构、补齐最小必要验证，最终同步周报与项目状态文档。

## 3. 六阶段执行方案

### 阶段 1：输入收集与证据建立

- 统计最近 7 天提交记录与改动范围
- 汇总核心文件、主要主题和热点目录
- 读取与本周改动强相关的需求、规则、状态文档
- 输出可追溯的输入清单与证据路径

### 阶段 2：改动主题识别

- 按模块整理本周功能开发、缺陷修复、文档治理、工具链调整
- 判断热点是否集中于 API 层、Repository 层、领域模型、异步任务、客户端脚本、测试基建
- 形成“改动目的 / 风险区域 / 结构性问题候选”概览

### 阶段 3：六维度深度评审

- 从架构一致性、可读性、可靠性、稳定性、可测试性、可维护性 6 个维度分析
- 对每个关键问题记录：
  - 证据位置
  - 影响范围
  - 严重程度
  - 建议处理方式
- 将问题分级为“立即实施 / 建议纳入下周 / 暂缓处理”

### 阶段 4：立即实施项筛选

- 仅保留高价值、低风险、可回滚、可验证的修改项
- 优先考虑：
  - 高频重复逻辑
  - 明显职责混乱或越层调用
  - 潜在稳定性与可靠性缺陷
  - 高回归风险但测试缺口明显的关键链路
- 对每个候选项确认最小修改面、验证方式和回滚路径

### 阶段 5：小步重构与验证

- 仅在证据充分的前提下实施“立即实施”项
- 修改业务代码时，同步更新对应测试、文档或配置说明
- 优先执行与改动范围直接相关的 `ruff`、`mypy`、`pytest`
- 若验证失败且无法安全修复，则撤回高风险改动，并在报告中说明

### 阶段 6：沉淀与交付

- 生成或更新：
  - `docs/40-dev-loop/weekly-code-review/weekly-code-review-2026-08-22.md`
  - `docs/00-governance/project-status.md`
- 提炼本轮可复用的规范、检查清单或 skills 草案
- 若最终产生代码或文档修改，再按 Git 规范提交、推送，并谨慎核实用户要求中的分支合并动作是否适用于当前实际分支状态

## 5. 风险控制原则

- 不做无边界大规模重写
- 不为追求“更优雅”而改变既有行为
- 任何无法快速验证安全性的候选改动，一律降级为治理建议
- 修改 `services/*/app/` 时，必须同步更新 `services/*/tests/`
- 若发现本周无实质性代码改动，则只输出分析报告、治理建议与规范沉淀，不进行代码修改
- 若执行过程中发现异常工作区变更或分支状态与预期不一致，立即暂停并请求人工决策

## 6. 预期产出

- 一份周度代码分析与重构报告
- 一次项目状态文档同步更新
- 一组经过验证的高价值小步优化（如果存在安全可改的立即实施项）
- 一组下周继续治理建议
- 一组可复用规范或 skills 草案
