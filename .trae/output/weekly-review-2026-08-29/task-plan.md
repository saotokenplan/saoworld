# 每周代码审查与优化任务计划

> 任务日期：2026-08-29
> 执行角色：高级架构师 + 重构工程师
> 状态：待确认

## 1. 任务目标

围绕最近 7 天代码改动执行一次每周自动化审查，产出事实可追溯的分析结论、重构建议与治理沉淀，并在风险可控时实施小步重构。

## 2. 已确认输入事实

- `git log --since='7 days ago'` 返回空结果，最近 7 天无新提交。
- `git status --short --branch` 显示当前位于 `feature-prd`，工作区干净。
- 最近一次提交日期为 `2026-08-03`，已明显早于本次统计窗口。
- `docs/00-governance/project-status.md` 已记录自 `2026-07-27` 起运行时环境硬阻塞、连续多日无新代码合并的停滞态势。
- 最近可读周报为 `docs/40-dev-loop/weekly-report-2026-07-21.md`，时间窗口也早于本次统计窗口。

## 3. 本轮执行边界

### 3.1 允许执行

- 基于最近 7 天窗口输出“无实质代码改动”的周度分析结论。
- 更新周审查报告与项目状态文档中的周度质量结论、风险判断和治理建议。
- 在确认存在低风险、高价值且不依赖虚构事实的文档治理项时，做最小必要更新。
- 如发现与“无最近改动”结论冲突的新证据，再回到事实收集阶段重新判断。

### 3.2 暂不执行

- 未经确认直接实施业务代码深度重构。
- 编造不存在的最近 7 天改动主题、测试结果或完成状态。
- 在没有最近改动样本的前提下，强行做“按本周改动热点”的代码重写。
- 直接执行 `git commit`、`git push`、分支切换、合并和删除分支流程。

## 4. 分阶段执行方案

### 阶段 A：事实补证

- 核对最近 7 天提交、工作区状态、最近一次提交日期。
- 读取需求、里程碑、状态、周报与相关工程规则。
- 输出“本周是否存在可审查代码改动”的事实判断。

### 阶段 B：周度分析

- 若最近 7 天无代码改动，则重点分析：
  - 为什么没有改动
  - 停滞风险如何影响 M4 实施
  - 现有热点模块的遗留结构风险
- 若发现窗口内存在遗漏改动，则补充改动概览和主题识别。

### 阶段 C：重构决策

- 仅在存在“低风险、边界清楚、无需假设近期改动背景”的问题时，列入“立即实施”。
- 预计优先级：
  - 立即实施：文档治理与周度审查产出
  - 建议下周：运行时环境恢复后的热点模块深查
  - 暂缓处理：依赖真实环境或缺乏近 7 天改动样本的重构项

### 阶段 D：落盘与验证

- 生成 `docs/40-dev-loop/weekly-code-review/weekly-code-review-2026-08-29.md`。
- 更新 `docs/00-governance/project-status.md` 的周度质量状态与治理建议。
- 对文档改动执行最小必要自检。

### 阶段 E：提交与分支动作

- 仅在你确认继续执行后，才会评估是否进行 `git commit` / `push` / 合并。
- 若当前分支本身已是 `feature-prd`，会先提示该流程与“临时分支合并到 feature-prd”要求冲突，再请求你确认替代方案。

## 5. 风险判断

### 主要风险

- **统计窗口为空**：若强行输出“本周改动分析”，会产生编造风险。
- **分支流程冲突**：当前分支已经是 `feature-prd`，无法按原指令“切回 feature-prd 并合并当前临时分支”直接执行。
- **环境阻塞持续**：即使执行重构，也难以完成真实运行时验证。

### 控制策略

- 以 git 事实为唯一依据，窗口为空则明确写“无实质改动”。
- 把无法安全执行的代码重构转为治理建议，不强行落地。
- 在进入提交与分支步骤前再次与你确认分支策略。

## 6. 预期交付物

- 一份周度代码分析与治理报告。
- 一次项目状态同步更新。
- 一份本轮可复用的审查/治理清单沉淀。
- 如你确认继续执行，附带最小必要的文档修改与验证结果。
