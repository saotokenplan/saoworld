# Weekly Code Review Task Plan

> 任务名称：每周代码审查与重构优化
> 执行日期：2026-09-05
> 统计窗口：2026-08-29 至 2026-09-05
> 当前分支：`feature-prd`
> 当前阶段：规划中，待用户确认后执行

## 1. 任务目标

在最近 7 天真实代码改动的基础上，完成可追溯的系统性周度代码分析，识别高价值、低风险、可回滚的治理项，并仅在风险可控前提下实施小步深度重构、补齐最小必要验证，最终同步周报与项目状态文档。

## 2. 已确认约束

- 统计窗口固定为最近 7 天
- 必须优先关注 `services/`、`workers/`、`game/`、`tools/`、`docs/`
- 必读文档至少包含：
  - `docs/10-requirements/需求迭代计划.md`
  - `docs/10-requirements/项目里程碑与验收标准.md`
  - `.trae/rules/10-python-backend.md`
  - `.trae/rules/41-testing.md`
- 需补充读取热点模块直接相关的规范、最近项目状态文档和最近周报
- 仅对“立即实施”项落地修改，不做无边界大规模重写
- 修改业务代码时必须同步更新相关测试、文档或配置说明
- 若无法确认安全性，则降级为治理建议，不直接修改

## 3. 六阶段执行方案

### 阶段 1：输入收集与证据化

- 获取最近 7 天提交记录、改动目录、核心文件和主要变更主题
- 聚焦 `services/`、`workers/`、`game/`、`tools/`、`docs/` 的真实变更
- 读取需求、规范、状态文档和最近周报
- 建立“本周改动证据清单”，避免凭印象下结论

### 阶段 2：本周改动主题识别

- 按模块归类本周改动：功能开发、缺陷修复、测试补强、工具链、文档治理
- 判断热点是否集中在 API 层、Repository 层、领域模型、异步任务、客户端脚本、测试基建等区域
- 输出本周改动概览、风险区域和结构性问题候选

### 阶段 3：六维深度分析

- 从架构一致性、可读性、可靠性、稳定性、可测试性、可维护性 6 个维度分析热点改动
- 对每个关键问题记录：
  - 证据文件
  - 影响范围
  - 严重程度
  - 建议动作
- 将问题归类为：
  - 立即实施
  - 建议纳入下周
  - 暂缓处理

### 阶段 4：立即实施项设计

- 仅筛选高价值、低风险、可回滚、可验证的优化项
- 优先考虑：
  - 结构性重复逻辑
  - 明显越层或职责混乱
  - 稳定性或可靠性隐患
  - 高回归风险测试缺口
- 对每个候选项确认：
  - 不偏离当前需求目标
  - 修改范围可控
  - 可由静态检查、类型检查和目标测试验证
  - 回滚路径清晰

### 阶段 5：执行重构与验证

- 在确认后按小步方式实施“立即实施”项
- 修改 `services/`、`workers/` 或 `game/` 时，同步更新对应测试
- 优先运行与改动范围直接相关的 `ruff`、`mypy`、`pytest`
- 进行最小必要回归验证；若验证失败且无法安全修复，则回退高风险改动并保留分析结论

### 阶段 6：沉淀与交付

- 生成或更新：
  - `docs/40-dev-loop/weekly-code-review/weekly-code-review-2026-09-05.md`
  - `docs/00-governance/project-status.md`
- 沉淀规范、检查清单、模板或 skills 草案
- 若最终执行了代码修改，再评估并执行 Git 提交与推送

## 5. 风险控制原则

- 不做无边界重写
- 不因“更优雅”而改变既有行为
- 对缺少证据或缺少验证手段的改动，降级为建议项
- 若发现与当前任务无关的异常工作区变更，立即暂停并请求人工决策
- 先分析后修改，先验证后保留
