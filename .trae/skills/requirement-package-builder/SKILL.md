# requirement-package-builder

## 目标

把产品目标、玩法讨论和技术边界收束成可直接进入 AI coding 闭环的需求包。输出结果必须让后续 Agent 能直接实现、验证和回滚，而不是停留在概念层。

## 适用场景

- 新功能从 0 到 1 进入研发前
- 需求已经讨论过，但还没有形成机器可执行的验收输入
- 现有方案需要拆成更细的任务包

## 规范来源

- 主要来源：
  - `docs/20-specs/product-spec.md`
  - `docs/20-specs/agent-loop-spec.md`
- 次要来源：
  - `docs/20-specs/engineering-conventions.md`
- 说明：
  - 产品目标、范围、非目标和验收口径以 `product-spec.md` 为准
  - 需求包结构、门禁闭环和回滚约束以 `agent-loop-spec.md` 为准
  - 工程拆分边界和协作约束参考 `engineering-conventions.md`

## 输入

- 产品目标
- 范围与非目标
- 既有需求文档
- 技术边界与已有约束
- 当前版本上下文

## 输出

必须产出以下四类文件：

- `spec.md`
- `acceptance.md`
- `risk.md`
- `tasks.md`

必要时补充：

- `api-notes.md`
- `content-scope.md`
- `rollback-notes.md`

## 工作流程

1. 先明确目标用户、目标行为和非目标
2. 把需求压缩成一条可验收主线
3. 把验收语句写成可映射到测试和门禁的表达
4. 识别风险与边界
5. 将任务拆成可以在单轮循环内完成的原子任务

## 硬约束

- 一个需求包只能有一个主目标
- 每项任务都必须写清修改范围和依赖关系
- `acceptance.md` 里不能只有模糊描述，必须有可判断的结果
- `risk.md` 必须覆盖功能、内容、发布和回滚风险
- 不写“顺手优化”“顺手重构”这类隐性扩 scope 内容

## 输出格式要求

### `spec.md`

至少包含：

- 目标
- 范围
- 非目标
- 用户路径
- 关键约束

### `acceptance.md`

至少包含：

- 前置条件
- 操作步骤
- 期望结果
- 失败条件
- 对应 gate 或测试类型

### `risk.md`

至少包含：

- 风险名称
- 触发条件
- 影响范围
- 缓解方式
- 回滚方式

### `tasks.md`

至少包含：

- 任务编号
- 任务目标
- 输入
- 输出
- 依赖
- 验收信号

## 不该做的事

- 不直接进入代码实现
- 不跳过非目标定义
- 不把内容审核、数值边界和回滚约束留给后面再补
