# 文档生命周期与状态规范

## 目的

本文档用于统一 `docs/` 体系中的文档状态定义、状态切换条件和标注方式，减少“文档存在但是否生效不清楚”“目标态设计和当前可执行内容混在一起”“已过期文档没有显式退场标识”的问题。

## 适用范围

- 适用于 `docs/` 目录下的全部文档。
- 适用于 `.trae/skills/` 中引用 `docs/` 的场景说明和规范来源同步判断。
- 适用于新增、修订、迁移、重命名、合并、废弃和归档等变更。

## 基本原则

- 每份文档都应能回答“当前是否有效”“是否可直接执行”“是否仍应继续维护”。
- 文档状态用于表达维护与使用方式，不替代目录分层和权威关系。
- 同一主题若已存在更高权威或更新版本，应优先推动状态切换，而不是长期并行维护多份等价文档。
- 目标态设计可以保留，但必须显式标注，不能伪装成当前立即可执行规范。
- 现有存量文档允许渐进补标；未一次性回填时，应在后续修订中补上状态说明。

## 标准状态

### `draft`

- 含义：
  - 草稿阶段，内容仍在快速补充或调整。
- 适用场景：
  - 新建文档初稿
  - 尚未完成自检或评审
  - 仅形成方向，尚未形成稳定口径
- 使用要求：
  - 不作为最终执行基线
  - 可被引用为讨论材料，但不能替代 `20-specs/` 的正式规范

### `active`

- 含义：
  - 当前生效并应继续维护的正式文档。
- 适用场景：
  - 已通过当前阶段评审
  - 已具备稳定定位和清晰边界
  - 允许作为当前协作和实施参考
- 使用要求：
  - 若属于执行约束，必须与 `20-specs/` 权威关系保持一致
  - 若属于入口或治理文档，修改后要同步相关入口和引用

### `deprecated`

- 含义：
  - 已不建议继续作为主要入口或主要依据使用，但短期内仍保留。
- 适用场景：
  - 已有新文档替代
  - 即将迁移、合并或下线
  - 内容仍可能被历史引用，但不应继续扩展
- 使用要求：
  - 必须写清替代文档或退场原因
  - 不再新增实质内容，只允许补充迁移说明和清理引用

### `archived`

- 含义：
  - 已归档，仅作为历史背景、决策记录或审计留存保留。
- 适用场景：
  - 历史调研
  - 已完成使命的阶段性说明
  - 已被正式规范彻底替代的保留资料
- 使用要求：
  - 不再作为当前执行输入
  - 原则上不再持续维护，除非修正明显事实性错误或补充归档说明

## 推荐状态流转

标准流转建议如下：

`draft -> active -> deprecated -> archived`

补充说明：

- 并非所有文档都必须经历全部阶段。
- 调研类文档可在完成结论后直接从 `draft` 进入 `archived`。
- 错误建档或重复文档可从 `draft` 直接删除，但删除前仍需按变更流程清理引用。
- 若已废弃文档因外部依赖暂时无法下线，可长期停留在 `deprecated`，但必须写明原因。

## 状态切换条件

### `draft -> active`

至少满足以下条件：

- 文档目的、适用范围和与其他文档的关系已写清。
- 已完成基本自检，内容没有明显重复或层级错误。
- 若属于入口型、治理型或执行型文档，相关责任人已确认其定位。
- 必要的入口文档和引用路径已同步。

### `active -> deprecated`

出现以下任一情况时应考虑切换：

- 已存在新的正式替代文档。
- 现有文档仍有历史价值，但已不应继续作为主要依据。
- 目录结构或规范体系调整后，该文档只保留过渡用途。

### `deprecated -> archived`

至少满足以下条件：

- 已完成主要引用清理。
- 已有明确替代路径，或确认仅保留为历史记录。
- 保留原因清晰，不会再被误当作当前有效规范。

## 标注方式

建议在文档标题下方增加状态说明块：

```md
> 文档状态：active
> 适用阶段：当前
> 维护要求：持续维护
```

如果文档已废弃或归档，建议增加替代说明：

```md
> 文档状态：deprecated
> 替代文档：`docs/20-specs/backend-data-spec.md`
> 说明：本文件仅保留历史上下文，不再继续扩展
```

## 默认状态建议

- `00-governance/`
  - 默认应为 `active`
  - 若仅保留阶段性说明，可标为 `archived`
- `10-requirements/`
  - 默认应为 `active` 或 `archived`
  - 已被更明确规范吸收且只保留立项背景时，可转为 `archived`
- `20-specs/`
  - 默认应为 `active`
  - 原则上不应长期保留 `deprecated` 状态的规范文档
- `30-api/`
  - 默认应为 `active`
  - 草案型接口说明可临时使用 `draft`
- `40-dev-loop/`
  - 可为 `active` 或 `draft`
  - 若内容偏目标态但暂未实施，必须在正文中明确说明
- `50-research/`
  - 常见状态为 `archived`
  - 若仍持续影响当前选型，也可暂为 `active`

## 与权威关系的配合规则

- 文档状态不改变目录层级的权威关系。
- 即使 `10-requirements/` 文档标记为 `active`，若与 `20-specs/` 冲突，仍以 `20-specs/` 为准。
- `30-api/` 中的 `active` 文档仍属于接口参考索引，不替代 `20-specs/` 中的执行规范。
- `.trae/skills/` 若引用了 `deprecated` 或 `archived` 文档，应尽快改为引用仍然 `active` 的上游文档。

## 状态维护责任

- 文档作者或当前维护责任人负责首次标注文档状态。
- 流程治理责任人负责治理类文档的状态口径一致性。
- 技术规范责任人负责 `20-specs/` 和 `30-api/` 中关键执行文档的状态确认。
- 当文档状态变为 `deprecated` 或 `archived` 时，维护责任人应同步检查入口、映射和 Skill 引用。

## 最小执行要求

- 新增文档默认先视为 `draft`，除非创建时已完成完整评审。
- 入口型文档、治理文档、执行规范文档在稳定后应尽快转为 `active`。
- 被替代但尚未清理完成的文档必须显式标记为 `deprecated`，不能继续保持无状态。
- 需要长期保留但不再作为当前输入的文档，应转为 `archived`。
