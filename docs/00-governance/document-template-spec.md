# 文档模板规范

## 目的

本文档用于统一治理文档、规范文档和 API 文档的标准章节结构，减少“同类文档写法差异过大”“该写什么靠临场发挥”“新增文档缺目的、缺边界、缺关系说明”的问题。

## 适用范围

- 适用于 `docs/00-governance/` 下的治理文档。
- 适用于 `docs/20-specs/` 下的执行规范文档。
- 适用于 `docs/30-api/` 下的接口参考文档。
- 其他目录中的文档可参考本规范，但可按实际需要裁剪。

## 使用原则

- 模板用于统一下限，不要求机械复制全部章节。
- 同类文档优先保持同一结构风格，避免每份文档都自创目录。
- 若文档较短，可删去不必要章节，但必须保留核心信息。
- 若文档属于入口型、治理型或执行型文档，建议补充文档状态说明，状态定义以 `docs/00-governance/document-lifecycle.md` 为准。
- 若文档内容跨越多个层级，应优先拆文档，而不是在一份文档中混写背景、规范和接口细节。

## 通用最小骨架

以下内容适用于大多数正式文档：

```md
# 标题

> 文档状态：active
> 适用阶段：当前
> 维护要求：持续维护

## 目的

## 适用范围

## 当前定位

## 主体内容

## 与其他文档的关系
```

最小要求说明：

- `标题`
  - 应准确表达文档主题，不使用过泛命名。
- `文档状态`
  - 对治理文档、规范文档、入口文档优先补充。
- `目的`
  - 回答“为什么要有这份文档”。
- `适用范围`
  - 回答“这份文档管什么，不管什么”。
- `当前定位`
  - 回答“它在整套文档体系中扮演什么角色”。
- `主体内容`
  - 根据文档类型展开。
- `与其他文档的关系`
  - 说明上游、下游、权威关系或引用关系。

## 一、治理文档模板

适用对象：

- `docs/00-governance/document-directory-spec.md`
- `docs/00-governance/document-change-process.md`
- `docs/00-governance/document-lifecycle.md`
- `docs/00-governance/document-ownership.md`
- `docs/00-governance/document-review-checklist.md`

推荐章节：

```md
# 文档标题

> 文档状态：active
> 适用阶段：当前
> 维护要求：持续维护

## 目的

## 适用范围

## 当前定位

## 基本原则

## 核心规则

## 例外情况或裁剪说明

## 最小执行要求

## 与其他文档的关系
```

章节说明：

- `基本原则`
  - 提炼 3 到 5 条高层规则，帮助读者先理解方向。
- `核心规则`
  - 写清流程、标准、责任分配、检查点或裁定规则。
- `例外情况或裁剪说明`
  - 说明哪些情况可以简化、延期或特殊处理。
- `最小执行要求`
  - 定义“至少做到什么才算遵守”。

不建议遗漏的要素：

- 是否说明该文档约束的是谁。
- 是否说明何时必须同步入口、映射或引用。
- 是否说明与 `20-specs/`、`.trae/skills/`、`docs/README.md` 的关系。

## 二、规范文档模板

适用对象：

- `docs/20-specs/product-spec.md`
- `docs/20-specs/backend-data-spec.md`
- `docs/20-specs/content-generation-spec.md`
- `docs/20-specs/agent-loop-spec.md`
- `docs/20-specs/engineering-conventions.md`

推荐章节：

```md
# 文档标题

> 文档状态：active
> 适用阶段：当前
> 维护要求：持续维护

## 目的

## 适用范围

## 当前定位

## 设计目标或约束目标

## 核心定义

## 规则与约束

## 边界与非目标

## 验收或检查要点

## 与其他文档的关系
```

章节说明：

- `设计目标或约束目标`
  - 写清该规范要保证什么，不只是描述现状。
- `核心定义`
  - 定义术语、对象、角色、状态、模块边界或数据实体。
- `规则与约束`
  - 这是规范正文核心，应尽量明确到可执行、可校验。
- `边界与非目标`
  - 防止规范不断膨胀，把不属于本文件的内容挡在外面。
- `验收或检查要点`
  - 说明什么算满足规范，便于后续拆任务和评审。

不建议遗漏的要素：

- 是否写清该文档是否为执行基线。
- 是否区分“目标态设计”和“当前必须执行”。
- 是否避免把 API 样例、调研背景、流程说明混成一份文档。

## 三、API 文档模板

适用对象：

- `docs/30-api/api-overview.md`
- `docs/30-api/api-permissions.md`
- `docs/30-api/api-error-codes.md`
- `docs/30-api/api-examples-vote.md`
- 后续 `openapi-draft.md`

推荐章节：

```md
# 文档标题

> 文档状态：active
> 适用阶段：当前
> 维护要求：持续维护

## 目的

## 适用范围

## 当前定位

## 前置约定

## 核心清单或接口主体

## 示例或约束说明

## 异常与边界情况

## 与其他文档的关系
```

章节说明：

- `前置约定`
  - 说明认证方式、角色、版本前缀、返回包结构、幂等约束等通用信息。
- `核心清单或接口主体`
  - 根据文档类型写接口列表、权限矩阵、错误码表或请求响应样例。
- `示例或约束说明`
  - 补充请求示例、响应示例、字段约束、状态流约束。
- `异常与边界情况`
  - 说明权限不足、状态冲突、空结果、幂等重放或回滚场景。

不建议遗漏的要素：

- 是否说明该文档是“接口参考索引”而非替代 `20-specs/`。
- 是否与权限、错误码、样例之间保持一致。
- 是否补充最小可执行样例，而不是只列标题。

## 四、模板裁剪规则

- 文档较短时，可把 `当前定位` 合并进 `目的` 或 `适用范围`。
- 文档以清单为主时，可把 `核心定义` 与 `规则与约束` 合并。
- 文档以样例为主时，可把 `示例或约束说明` 扩展为多个分节。
- 若文档属于历史归档，不必强行补齐所有执行型章节，但应明确 `文档状态` 和保留原因。

## 五、不建议的写法

- 没有 `目的`，导致读者不知道为什么要读这份文档。
- 没有 `适用范围`，导致不同层级内容混写。
- 没有 `与其他文档的关系`，导致权威关系不清。
- 规范文档大量堆背景，真正约束只有几句。
- API 文档只有接口路径，没有前置约定、错误码或示例。
- 治理文档只有原则口号，没有流程、责任或检查点。

## 六、落地建议

- 后续新增治理文档时，优先按“治理文档模板”起草。
- 后续新增执行规范时，优先按“规范文档模板”起草。
- 后续新增接口文档时，优先按“API 文档模板”起草。
- 对现有关键入口文档，可在后续修订时逐步补齐 `文档状态`、`当前定位` 和 `与其他文档的关系` 三类缺口。

## 与其他文档的关系

- 目录分层以 `docs/00-governance/document-directory-spec.md` 为准。
- 新增与修订流程以 `docs/00-governance/document-change-process.md` 为准。
- 文档状态说明以 `docs/00-governance/document-lifecycle.md` 为准。
- 维护责任以 `docs/00-governance/document-ownership.md` 为准。
- 评审检查项以 `docs/00-governance/document-review-checklist.md` 为准。
