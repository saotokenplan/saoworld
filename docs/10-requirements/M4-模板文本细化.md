# M4 模板文本细化

> 文档状态：draft
> 适用阶段：M4 实施期（提示词硬化文本已于 2026-07-25 落地至 live prompt，见第五节实施期落地记录）
> 维护要求：随 WP1 推进持续维护
> 关联工作包：M4-WP1 生成模板验收收口

## 目的

本文档定义 M4「生成模板验收收口」（WP1）的**模板文本细化方案**：以装备、怪物（含 Boss）、场景三类生成模板为对象，在规划期完成模板文本的现状盘点、缺陷定位与可直接应用的细化文本设计，用于：

1. 承载差距 G1（装备模板）、G2（怪物模板）、G3（场景描述模板）的规划期收口——把「字段完整度实测 >95%」「章节上限校验」「强度区间约束」三个验收点的文本层准备先行固化；
2. 为 WP1 实施期（真实 LLM 实测）提供明确的修改对象与验收基线，避免实施期边测边改、口径漂移；
3. 为 WP2 样本集标注提供「数值合理性」标签的判定基准（本文第三节数值锚定表即标注口径）。

本文档原始定位为规划期文本层设计与差距登记（不修改 `services/` 代码，继承「不抢跑」约束）。进入 M4 实施期后，第三节的硬化文本已落地至 `services/generation/app/core/content_generator.py` 的 live prompt 函数（见第五节「实施期落地记录」）；A1 双源收口实施时会将这些文本一并迁移至 jinja2 模板。

## 适用范围

- 覆盖装备（item）、怪物（monster）、Boss（monster_boss）、场景（region_description）四类生成对象的提示词文本。
- 覆盖提示词文本与质量评分器（`quality_scorer.py`）、数据适配器（`*_data_adapter.py`）之间的字段契约一致性。
- 不覆盖 NPC / 任务 / 聚落模板（M3 已验收，不在 M4 差距清单内；其双源问题并入 F0 统一登记）。
- 不覆盖审核阈值调优（属 WP2）、审核效率指标（属 WP3）、发布串联（属 WP4）。

## 当前定位

## 一、现状盘点：双源提示词与字段契约

### 1.1 双源提示词现状（关键背景）

生成服务存在**两套提示词文本**，且已发生漂移：

| 源 | 位置 | 状态 |
|----|------|------|
| 内联提示词（live） | `services/generation/app/core/content_generator.py` 的 `_build_*_prompt()` 与 `_build_system_prompt()` | **实际生效**：`generate_npc/quest/region/monster/boss/item` 全部调用内联构造函数出 prompt |
| jinja2 模板文件（dead） | `services/generation/templates/**/*.jinja2`（16 个文件） | **未接线**：各 `generate_*` 方法仅解析模板名（`get_*_template_by_type`），随后丢弃模板、改用内联 prompt；模板文件仅被 `TemplateManager` 登记与两个旧测试（`test_npc_template.py`、`test_quest_template.py`）引用 |

漂移实例（实测比对）：

- Boss：jinja2 `monster_boss.jinja2` 未请求 `is_boss / boss_rank / phase_count / special_skills / enrage_threshold / reward` 六个字段，且使用 `behavior_pattern.phases` 嵌套结构；live `_build_boss_prompt` 已包含全部六字段与扁平结构（与评分器、适配器一致）。
- 装备：jinja2 要求 stats 细分字段逐项列出，live prompt 为概括式描述；措辞与约束均有出入。
- 怪物：jinja2 与 live 在 `behavior_pattern`、`skills` 字段描述细节上不一致。

**含义**：WP1 实施期实测必须以 live 内联 prompt 为修改与测量对象；若以 jinja2 模板文件为验收对象，将测错目标。

### 1.2 字段契约对照（live prompt vs 评分器 vs 适配器）

| 对象 | live prompt 字段 | 评分器必填 | 适配器必填 | 一致性 |
|------|------------------|------------|------------|--------|
| 装备 | item_key/type/slot/name/description/rarity/chapter_id/level_requirement/stats/effects/sell_price/stackable | 同左 8 项必填 + stats/effects 结构校验 | 一致 | ✅ 基本一致 |
| 怪物 | monster_key/name/type/chapter_id/region_key/level/hp/attack/defense/speed/description/behavior_pattern/loot_table/skills | 同左 14 项必填 | 一致 | ✅ 一致 |
| Boss | 怪物 14 项 + is_boss/boss_rank/phase_count/special_skills/enrage_threshold/reward/min_reputation | 怪物 13 项 + 六字段必填（缺 min_reputation） | 六字段必填 | ✅ live 侧一致（jinja2 侧缺失，见 F0） |
| 场景 | region_key/name/chapter_id/region_type/parent_region/description/lore/atmosphere/visual_style/landmarks/danger_level/recommended_level/accessibility/climate/notable_locations | 仅校验 name/description + **difficulty**（easy/normal/hard/extreme）+ **features** | 使用 **danger_level**（peaceful/low/medium/high/extreme）+ **landmarks** | ❌ 评分器与 prompt/适配器错位（见 F1） |

| # | 缺陷 | 位置 | 影响 | 严重度 |
|---|------|------|------|--------|
| F0 | 双源提示词漂移：jinja2 死模板与 live 内联 prompt 内容不一致，Boss jinja2 缺 6 个评分器必填字段 | `templates/` 全目录 vs `content_generator.py` | 若以模板文件为验收对象将测错目标；新成员易被误导；模板文件按现状永远无法通过评分（缺字段每项 -0.03，Boss 六项即 -0.18，>0.85 不可达） | 高 |
| F1 | `score_region` 校验 `difficulty`（easy/normal/hard/extreme）与 `features`，而 live prompt 与适配器使用 `danger_level`（peaceful/low/medium/high/extreme）与 `landmarks` | `quality_scorer.py::score_region` | 场景生成评分口径与实际产出字段错位：`difficulty` 恒为缺省、`features` 恒为空列表，枚举校验永不命中，场景评分维度名存实亡 | 高 |

| F4 | 章节强度上限无文本载体：装备 `level_requirement`、怪物 `level`、场景 `recommended_level` 与章节号之间无任何映射条款 | 三类 live prompt | G1/G2 的「章节上限校验」在 prompt 层没有可执行约束，只能靠事后评分兜底 | 中 |

## 三、细化方案（可直接应用的文本设计）

以下文本块为实施期写入 live prompt 的候选内容（规划期不落地）。数值为设计初值，实施期按真实输出分布回归校准（走 WP2 变更流程）。

### 3.1 装备数值锚定表（F2）

拟追加到 `_build_item_prompt` 输出要求尾部：

```text
数值锚定（必须落在以下区间，允许 ±20% 浮动）：
- weapon 的 attack 基值 = 6 + 4 × level_requirement，乘以稀有度系数
- armor 的 defense 基值 = 3 + 2.5 × level_requirement，乘以稀有度系数
- 稀有度系数：common=1.0，uncommon=1.2，rare=1.5，epic=1.9，legendary=2.4
- max_hp 加成 ≤ 50 × level_requirement × 稀有度系数；max_mp 同理上限减半
- critical_rate 上限：common 0.05 / uncommon 0.08 / rare 0.12 / epic 0.16 / legendary 0.20
- critical_damage 区间 1.2-2.5，随稀有度递增
- sell_price 基值 = 10 × level_requirement × 稀有度系数（取整）
```

### 3.2 怪物数值锚定表（F3）

拟追加到 `_build_monster_prompt` 输出要求尾部：

```text
数值锚定（必须落在以下区间，允许 ±20% 浮动）：
- hp 基值 = 40 + 26 × level，乘以类型系数
- attack 基值 = 3 + 2.2 × level，乘以类型系数
- defense 基值 = 2 + 1.5 × level（不乘类型系数）
- 类型系数：beast=1.0，humanoid=0.9，undead=1.1，mechanical=1.2，elemental=0.95，demon=1.15，dragon=1.3
- speed 维持 1-20，与体型/类型相符（dragon/mechanical 偏慢，elemental 偏快）
- skills 的 damage_multiplier 区间 0.8-2.0（普通怪物），cooldown ≥ 3 秒
```

Boss 沿用现有倍数口径并在文本中显式化：`hp ≥ 5 × 同等级普通怪物基值`、`attack ≥ 2 ×`、`experience 3-5 ×`（live prompt 已有下限表述，补充「同等级普通怪物基值」引用 3.2 公式即可闭环）。

### 3.3 章节强度上限条款（F4）

拟追加到三类 prompt 尾部（一致性自检条款）：

```text
章节一致性约束：
- 本章为 chapter_N 时，装备 level_requirement 不得高于 10 × N
- 怪物 level 必须落在 [10 × (N-1) + 1, 10 × N + 2] 区间
- 场景 recommended_level 必须与上述怪物等级带一致
- 生成后请自检：所有数值字段是否同时满足数值锚定与章节上限，不满足请修正后再返回
```

章数上限与章节-等级带映射的权威口径以 `content-generation-spec.md` 及 world-service 导入校验为准，实施期对齐后回填本节。

### 3.4 输出格式硬化（F6）

拟统一追加到全部生成 prompt 末尾：

```text
输出格式要求：
- 仅返回一个 JSON 对象，不要返回任何解释文字、前后缀或 markdown 代码围栏
- 返回前逐项自检上述必需字段：缺失任一字段即视为不合格输出，请补全后再返回
```

few-shot 示例策略：示例素材取自 WP2 样本集（`M4-审核样本集设计.md`）中的「应过」合格件，每类对象 1 例，实施期以可选开关接入（避免 token 成本常驻），接入与否对 K1 通过率的影响纳入 WP2 回归观测。

### 3.5 双源收口方案（F0，实施期决策项）

两个候选方向：

- **方案 A（推荐）**：以 jinja2 模板文件为唯一源——将 live 内联 prompt 迁移回模板文件，`generate_*` 改为 `template_manager.render()` 渲染。优点：模板可独立评审/版本化，与 test_npc_template 等既有测试同构；缺点：需改动 `generate_*` 调用链。
- **方案 B**：以 live 内联 prompt 为唯一源——删除 16 个死 jinja2 文件与 `TemplateManager` 相关登记，保留两个旧测试需同步改写。优点：改动面小；缺点：提示词继续散落在代码中，不利于 WP2/WP4 的模板治理（模板 100% 抽检、版本留痕）。

建议方案 A，与 WP4 运营流程「新模板 100% 抽检」的治理方向一致；实施期第一个 sprint 内完成迁移与回归。

### 3.6 `score_region` 口径对齐（F1，实施期代码项）✅ 已落地

将 `score_region` 的校验字段与 live prompt / 适配器对齐：

| 评分器现状 | 对齐目标 | 说明 | 状态 |
|------------|----------|------|------|
| `difficulty`（easy/normal/hard/extreme） | `danger_level`（peaceful/low/medium/high/extreme） | 直接改字段名与枚举集 | ✅ 已落地（2026-07-23，auto-20260723-2246） |
| `features`（数组） | `landmarks`（数组，元素含 landmark_key/name/description/type/significance） | 补非空与元素结构校验 | ✅ 已落地（2026-07-23，auto-20260723-2246） |

规划期不改评分器代码；实施期修改时须同步更新 `services/generation/tests/test_quality_scorer.py` 并回填本表为「已落地」。本轮已落地：`quality_scorer.py::score_region` 改为校验 `danger_level`（5 值枚举）与 `landmarks`（非空列表 + 元素结构校验），测试 `test_quality_scorer.py` 同步更新（`test_score_region_valid` / `test_score_region_invalid_danger_level` / `test_score_region_missing_landmarks` / `test_score_region_landmark_missing_fields`）。
