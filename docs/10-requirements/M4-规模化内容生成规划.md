# M4 规模化内容生成规划

> 文档状态：active（规划期）
> 启动日期：2026-07-23
> 适用阶段：M4 规划与实施准备
> 维护要求：随 M4 推进持续维护

## 目的

本文档是 M4 里程碑「规模化内容生成」的规划主入口，回答四个问题：

1. M4 要达成什么（验收标准）？
2. 现状已经有什么（提前就位的骨架）？
3. 差距在哪里（需要收口的工作包）？
4. 按什么顺序、什么约束推进（排期与依赖）？

本文档不替代 `项目里程碑与验收标准.md` 的 M4 验收定义，也不替代 `需求迭代计划.md` 中 Sprint 10/11 的原始需求清单；两者是本规划的输入，本规划负责在**当前代码现状**之上做差距收口。

## 一、M4 验收标准（引用）

以 `docs/10-requirements/项目里程碑与验收标准.md` §2.4 为准：

| 类别 | 验收项 | 标准 |
|------|--------|------|
| 生成 | 装备生成模板 | AI 生成装备属性、描述，符合章节上限 |
| 生成 | 怪物生成模板 | AI 生成怪物属性、行为模式，强度合理 |
| 生成 | 场景描述生成 | AI 生成区域场景描述，符合世界观 |
| 审核 | 审核效率提升 | 自动审核通过率 >70%，审核时间 <30 分钟 |
| 发布 | 发布频率 | 每周至少 1 次区域更新 |
| 质量 | 生成质量稳定 | 连续 10 次生成质量评分 >0.8 |

里程碑名义日期：2027-03-01。由于项目实际进度显著领先名义排期（Sprint 9 已于 2026-07 收尾），实施排期见本文档第六节的重基线说明。

## 二、现状基线盘点（2026-07-23 代码口径）

M4 不是从零建设。盘点 `services/generation`、`services/review` 与 `workers` 后确认，M4 所需骨架已**提前就位**：

### 已就位能力

| 能力 | 现状 | 位置 |

| 生成器（7 类） | NPC / 任务 / 区域 / 聚落 / 怪物 / Boss / 装备生成方法均已实现 | `services/generation/app/core/content_generator.py` |
| 数据适配器（7 类） | 各类型生成结果到下游服务格式的适配器均已存在 | `services/generation/app/core/*_data_adapter.py` |
| 质量评分器 | 7 类对象各有独立评分方法 + 通用评分入口 | `services/generation/app/core/quality_scorer.py` |
| 生成模板 | monster_base / monster_boss / item_base / region_description / npc / quest / settlement 等 Jinja2 模板已落盘 | `services/generation/templates/` |
| 区域生成 API | `/ops/generation/regions` 已可用（对应原 S10-03） | `services/generation/app/api/routes.py` |
| 自动审核规则引擎 | 质量分数 / 内容安全 / 字段完整度 / 重复度四类规则已实现（对应原 S10-04） | `services/review/app/core/auto_review_engine.py` |
| 自动审核 API | `/ops/review/auto` 已可用（对应原 S10-05） | `services/review/app/api/routes.py` |

| 世界骨架校验 | 无骨架快照拒绝生成的约束已实现 | `services/generation/app/core/skeleton_validator.py` |
| 异步任务底座 | Celery app 与 beat schedule 已就绪 | `workers/` |

### 关键判断

- 原 Sprint 10 需求清单中的 S10-01 ~ S10-05（场景模板、适配器、API、审核规则引擎、审核 API）在**骨架层面已完成**，剩余工作是真实环境下的质量验证与调优，而非新建。
- M4 的真实差距集中在四类：**真实 LLM 质量稳定性、审核通过率调优、发布自动化、批量生成与效率**。
- 全部能力目前均未经过真实运行时验证（PostgreSQL / Redis / Docker / 真实 LLM 调用），与灰度发布共享同一验证前提。

|---|--------|------|------|----------|

## 四、工作包分解

在 `需求迭代计划.md` Sprint 10/11 原始清单基础上，按现状重排为五个工作包。原始 ID 保留映射，便于回溯。

### WP1 生成模板验收收口（原 S10-01/02/03 + S11-01）

- 装备、怪物、场景三类模板在真实 LLM 下的字段完整度实测（目标 >95%）。
- 章节上限与强度区间约束的端到端校验（生成 → 评分 → world-service 导入）。
- 模板调优：质量评分稳定 >0.85。
- 预估：4 人天。依赖：真实运行时环境。

### WP2 自动审核规则调优（原 S10-04 深化 + S11-02/03/04）

- 建立审核样本集：用真实生成结果标注「应过 / 应拒 / 应人工」基准。
- 阈值调优：质量分阈值、完整度阈值、相似度阈值基于样本集回归确定，目标自动通过率 >70% 且不误放高风险内容。
- 内容安全增强：敏感词库更新，高风险主题识别准确率 >90%。
- 重复度检测优化：同章节内容相似度阈值 <0.8 的实测验证。
- 预估：5 人天。依赖：WP1 产出真实样本。

### WP3 审核效率监控（原 S10-06）

- 自动审核通过率、审核耗时、人工介入率三项核心指标接入 Prometheus 与运营看板。
- 审核时间 <30 分钟的达标验证与告警。
- 预估：2 人天。依赖：无（可与 WP1 并行，但验证依赖 WP2）。

### WP4 发布自动化与周更节奏（原 S11-05 + 发布频率验收）

- 自动审核通过内容自动进入发布队列（审核 → 打包 → 发布串联）。
- 定义每周区域更新的运营流程：生成批次 → 自动审核 → 人工抽检 → 发布窗口。
- 灰度环境下的首次周更演练。
- 预估：4 人天。依赖：WP2 通过率达标、灰度发布完成。

### WP5 批量生成能力（原 S10-07）

- 确认现有生成链路对批量请求的支持程度，补齐批量入口（如需）。
- 批量生成的成本控制与失败隔离策略。
- 预估：3 人天。依赖：WP1。

### 验收工作包（原 S11-06）

- M4 里程碑验收：三项模板完整、通过率 >70%、周更达成、连续 10 次评分 >0.8。
- 产出：规模化生成验证报告、审核效率优化报告、M4 验收报告。

## 五、实施约束（不抢跑原则）

继承 `project-status.md` 的发布前约束，M4 工作按风险分级推进：

- **规划期（当前 → 灰度发布解锁）**：仅推进低风险准备 —— 模板文本细化、审核样本集设计、阈值调优预案、看板指标定义、运营流程草案。不改核心链路代码，不接入新的外部依赖。
- **实施期（灰度发布解锁后）**：按 WP1 → WP2/WP3 → WP4/WP5 顺序推进，全部工作包依赖真实运行时环境。
- **共享前提**：M4 与灰度发布共享 PostgreSQL / Redis / Docker / workers 运行时验证前提，运行时验证销项是 M4 实施的硬阻塞。

## 六、排期重基线说明

- `需求迭代计划.md` 中 Sprint 10（2026.12.02-12.15）与 Sprint 11（2026.12.16-12.29）的名义日期已与实际进度严重偏离，本文档不再沿用。
- M4 实施排期采用**依赖驱动**而非日期驱动：以「灰度发布窗口确认 + 运行时验证销项完成」为启动信号，启动后按 WP 顺序约 4-6 周完成实施与验收。
- 名义里程碑日期 2027-03-01 保持不变，当前判断有充足提前量；待灰度窗口确认后在周报中重基线具体日期。

## 七、风险与缓解

| 风险 | 级别 | 说明 | 缓解 |
|------|------|------|------|
| 运行时验证持续未闭环 | 高 | M4 全部实施工作包依赖真实环境 | 与灰度发布共用销项清单，随发布闭环一并解锁 |
| 真实 LLM 质量不达标 | 中 | 骨架基于 mock/受控输出验证，真实生成质量未知 | WP1 先行实测；质量评分阈值预留回退到人工审核的预案 |
| 审核通过率与内容安全互斥 | 中 | 通过率 >70% 的调优可能压低安全拦截率 | WP2 样本集必须包含高风险样本，安全规则一票否决不可调 |
| 周更节奏运营缺位 | 中 | 技术自动化达成后仍需运营执行 | WP4 同步产出运营流程草案，发布窗口与灰度节奏对齐 |
| LLM 成本随批量生成放大 | 低 | WP5 批量能力放开后 token 用量上升 | 沿用现有 budget_alert 阈值，批量入口默认带成本上限 |
