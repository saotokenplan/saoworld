## 任务目标与背景

vote-service 已完整实现并通过验证，具备完整投票生命周期管理能力。但 MVP 还需要世界内容基础服务作为支撑——所有内容生成、投票区域、内容包发布都依赖区域和章节概念。

根据 `backend-data-spec.md` 定义，`regions` 表是世界内容数据的核心基础表，API 规范已定义 `GET /api/v1/world/regions` 和 `GET /api/v1/world/regions/{region_id}` 接口。

**本次目标**：初始化 world-service 服务骨架，实现区域（regions）数据模型、玩家查询接口、运营管理接口、JWT 认证、统一响应 envelope、审计日志持久化，遵循 vote-service 已验证的架构模式。

- 创建 `WorldRepository` 类
- 方法：
  - `list_visible_regions(chapter_id)` - 玩家可见区域列表
  - `get_region_by_id(region_id)` - 区域详情
  - `create_region(...)` - 创建区域
  - `update_region_status(region_id, status)` - 更新区域状态
  - `list_all_regions(chapter_id, status, limit, offset)` - 运营全量查询

### 步骤 4：实现 Pydantic Schemas

- 通用 envelope 响应（EnvelopeResponse、PaginatedMeta、ErrorResponse）
- 区域相关：
  - `RegionResponse` - 区域响应模型
  - `RegionListResponse` - 区域列表响应
  - `CreateRegionRequest` - 创建区域请求
  - `UpdateRegionStatusRequest` - 更新状态请求
  - `RegionStatus` 枚举

### 步骤 5：实现 API 路由

- 健康检查：`GET /api/v1/health`
- 玩家接口（JWT + world:read scope）：
  - `GET /api/v1/world/regions` - 获取可见区域列表（分页）
  - `GET /api/v1/world/regions/{region_id}` - 获取区域详情
- 运营接口（JWT + ops scope）：
  - `POST /api/v1/ops/world/regions` - 创建区域
  - `POST /api/v1/ops/world/regions/{region_id}/status` - 更新区域状态
