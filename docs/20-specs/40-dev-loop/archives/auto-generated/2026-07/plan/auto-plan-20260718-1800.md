## 任务背景

项目当前处于 M3 里程碑推进阶段。根据 `docs/00-governance/project-status.md` 的"后续迭代方向"，中期任务包含「赛季排行系统」，目前尚未完成（无 ~~删除线~~ 标记），是 M3 里程碑里唯一剩余的未完成项。

上一轮任务（auto-20260718-1700）已完成 M3-04 跨服匹配系统，新增 5 张核心表（赛季、段位、队列、房间、结果）、5 个 Repository、14 个 API 端点、22 个测试用例。其中 `MatchSeason`、`PlayerRating`、`MatchResult` 表为赛季排行系统提供了数据基础，`MatchLeaderboardItem` Schema 与 `/player/match/leaderboard` 端点已具备最小可用版本。

但当前实现存在以下缺口：
1. **排行榜排序 bug**：`PlayerRatingRepository.get_leaderboard` 按 `desc(PlayerRating.tier)` 排序，因 tier 是字符串字典序，会出现 `silver > gold > diamond > bronze` 的错误顺序（正确应为 `challenger > master > diamond > platinum > gold > silver > bronze`）
2. **缺少玩家自身排名查询**：玩家无法查看自己在赛季中的具体名次
3. **缺少段位分布统计**：无法查看各段位的玩家数量分布
4. **缺少附近玩家查询**：玩家无法查看排名附近的对手
5. **缺少赛季结算与奖励发放机制**：`MatchSeason.reward_jsonb` 字段已预留但完全未消费，赛季结束后无奖励发放流程
6. **缺少历史赛季排行榜查询**：仅支持当前赛季，无法查询已结束赛季的排行

本轮任务在已有跨服匹配系统基础上，扩展完整的赛季排行能力，闭合 M3 里程碑最后一个核心功能。

## 核心设计

### 排序修复方案

使用 SQLAlchemy `case()` 表达式将 tier 字符串映射为整数索引后排序：

```python
from sqlalchemy import case

TIER_ORDER = ["bronze", "silver", "gold", "platinum", "diamond", "master", "challenger"]
tier_order_case = case(
    *[(PlayerRating.tier == t, i) for i, t in enumerate(TIER_ORDER)],
    else_=-1,
)
# order_by(desc(tier_order_case), PlayerRating.division, desc(PlayerRating.rating_points), desc(PlayerRating.wins))
```

### 排名计算方案

玩家自身排名采用子查询统计方式：

```python
# 计算排在当前玩家前面的玩家数 + 1
async def get_player_rank(player_id, season_id) -> int | None:
    rating = await self.get_player_rating(player_id, season_id)
    if rating is None:
        return None
    # 统计比当前玩家排名靠前的玩家数量
    better_count = await self.db.scalar(
        select(func.count()).where(
            and_(
                PlayerRating.season_id == season_id,
                # 比 (tier_index, -division, rating_points, wins) 更优
                ...
            )
        )
    )
    return better_count + 1
```

### 赛季结算状态机扩展

为避免污染 `MatchSeason.status` 现有状态机（`upcoming → active → ended → archived`），新增 `settlement_status` 字段：

- `unsettled`（默认）：未结算
- `settling`：结算中
- `settled`：已结算

迁移规则：`unsettled → settling → settled`，`settled` 为终态不可回退。

### 数据模型

新增 1 张表（season_reward_grants）：

- `SeasonRewardGrant`：赛季奖励发放记录（append-only 风格，支持幂等）
  - `grant_id` UUID 主键
  - `season_id` UUID 外键
  - `player_id` UUID 外键
  - `final_rank` Integer（结算时排名）
  - `final_tier` String(32)（结算时段位）
  - `final_division` Integer
  - `final_rating_points` Integer
  - `reward_payload_jsonb` JSONB（实际发放的奖励内容）
  - `status` String(32)：`pending`/`granted`/`failed`
  - `granted_at` TIMESTAMPTZ nullable
  - `idempotency_key` String(128) UNIQUE
  - `trace_id` String(64)
  - `schema_version` Integer 默认 1
  - `created_at` / `updated_at` 审计字段
  - `UNIQUE (season_id, player_id)` 防重发

### API 端点

**玩家侧（4 个，复用 `match:read` Scope）：**
- `GET /player/match/leaderboard/me` - 查询我的排名与段位详情
- `GET /player/match/leaderboard/tier-distribution` - 段位分布统计
- `GET /player/match/leaderboard/neighbors` - 附近玩家（前后各 N 名）
- `GET /player/match/rewards` - 我的赛季奖励列表

**运营侧（2 个，复用 `match:ops` Scope）：**
- `POST /ops/match/seasons/{season_id}/settle` - 赛季结算+奖励发放（含 Idempotency-Key）
- `GET /ops/match/seasons/{season_id}/rewards` - 赛季奖励发放列表

**已有端点扩展：**
- `GET /player/match/leaderboard` - 新增 `season_id` 可选参数，支持历史赛季查询

## 风险与回滚

- **风险 1**：修改 `MatchSeason` 表新增字段可能影响现有测试
  - 缓解：新增字段使用 `server_default` 保证旧数据兼容
- **风险 2**：赛季结算涉及大量玩家，可能在 Web 进程超时
  - 缓解：本轮实现同步版本（限制单次结算玩家数 ≤ 200），后续可扩展为 Celery 异步任务
  - 备注：M3 阶段玩家规模有限，同步实现可接受
- **风险 3**：排名计算使用子查询可能性能不佳
  - 缓解：使用复合索引 `(season_id, tier, division, rating_points, wins)` 优化
- **回滚路径**：删除新增的 SeasonRewardGrant 表和 season_reward_repo.py，恢复 routes.py / models.py / match_repo.py 到修改前状态
