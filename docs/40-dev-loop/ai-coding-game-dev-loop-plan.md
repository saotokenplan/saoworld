# AI Coding 驱动大型开放式游戏开发闭环实现方案

> 文档状态：active
> 适用阶段：当前
> 维护要求：持续维护

## 目标定义

你要的不是“让 AI 辅助写一些代码”，而是让 AI 成为整个游戏研发流水线的主执行者。也就是说，从需求拆解、方案设计、代码实现、资源生成、测试验证、构建发布，到上线后根据数据继续迭代，尽可能都由 AI 自动完成，形成一个能持续运行的研发闭环。

这件事要想真正落地，关键不是把更多步骤丢给大模型，而是把整个研发过程改造成一条 **文本优先、规则优先、可验证、可回滚** 的生产线。AI 只能在“输入清晰、边界明确、结果能验证”的环境里稳定工作，所以技术栈、项目结构、任务粒度和验收方式都要围绕这一点重构。

## 总体判断

完全由 AI coding 驱动整个游戏开发闭环，理论上可以做到 **80% 到 95% 的研发自动化**，但前提是项目从一开始就按 AI 可执行的方式设计。真正难的不是写出代码，而是保证：

1. AI 产出的代码和内容可以持续演进，不会几周后彻底失控。
2. 每一步都有明确输入和明确验收，不依赖隐性经验。
3. 游戏资源、逻辑、配置、测试和上线流程都能通过机器校验。
4. 每次迭代都是可追踪、可复现、可回滚的。

因此，建议把目标定义为：**AI-first 全流程研发体系**。默认由 AI 执行所有研发动作，人工只保留产品目标设定、关键审美判断和最终发布授权这三个高杠杆环节。如果你希望进一步减少人工，也可以继续把发布授权换成自动门禁，但那要建立在前面质量体系已经很成熟的前提下。

## 落地原则

### 1. 选 AI 友好的技术栈

如果项目要由 AI 持续编写、维护和重构，技术栈必须满足三个条件：可读性高、文本化程度高、CLI 友好。对于大型开放式游戏，我更建议优先采用以下组合：

| 层级 | 建议选型 | 原因 |
|------|----------|------|
| 游戏引擎 | `Godot 4` | 场景和脚本文本化程度高，版本控制友好，适合 AI 持续修改。 |
| 玩法脚本 | `GDScript` | 表达短、上下文集中、生成和修复速度快。 |
| 服务端 | `Python + FastAPI` | AI 生成、投票、规则审核和内容编排都适合 Python。 |
| 数据库 | `PostgreSQL` | 结构化数据、审计链路和版本追踪更稳定。 |
| 异步任务 | `Celery / Dramatiq` | 用于生成任务、审核任务、构建任务和回归任务。 |
| 基础设施 | `Docker + GitHub Actions / GitLab CI` | 便于把每个研发环节做成标准化流水线。 |
| 监控 | `Prometheus + Grafana + Sentry` | 跟踪生成质量、服务稳定性和线上异常。 |

不建议一开始选 `Unreal + C++` 作为主线方案。它当然更适合 3A 画面，但对 AI coding 来说上下文太重、编译反馈太慢、资产关系太复杂，不适合把整个闭环交给 AI 自动推进。对于“先跑通闭环”这件事，`Godot 4 + GDScript + Python` 的落地效率明显更高。

### 2. 一切都要文本化和结构化

AI 最怕两类东西：隐藏在界面里的状态，和没有结构的模糊信息。所以整个项目要尽量把这些对象变成文本：

1. 世界设定：放进 `yaml/json/markdown` 规则库。
2. 地图区域定义：用配置文件描述区域参数、资源等级、阵营分布。
3. NPC 模板：用结构化字段定义身份、阵营、性格、任务池。
4. 任务模板：用 DSL 或 JSON 描述目标、奖励、失败条件和触发器。
5. 技术任务：全部落到任务卡和验收标准文件。
6. 测试用例：全部可以命令行执行。

一旦信息仍然主要存在于脑子里、白板上、截图里、临时语音里，AI 就无法稳定接手。

### 3. 每个阶段都要自动验收

AI 执行一个步骤之后，不能靠“看起来差不多”来判断是否完成。必须让每一层都可校验：

1. 需求层：检查字段完整性、边界是否缺失。
2. 代码层：静态检查、单测、集成测试。
3. 引擎层：场景加载测试、关键节点存在性测试。
4. 内容层：世界观一致性检查、奖励边界检查、敏感内容检查。
5. 体验层：自动试玩脚本、路径穿透测试、卡死检测。
6. 发布层：构建成功、资源完整、回滚包可用。

没有自动门禁，所谓“AI 闭环”只会退化成“AI 不断写出越来越多没人敢发的东西”。

## 闭环架构

建议把整个系统拆成九个 AI 执行环节，每个环节都只做一件事，并把结果交给下一环节。

| 环节 | 目标 | 输入 | 输出 |
|------|------|------|------|
| 1. 目标编排 | 生成迭代目标和边界 | 愿景、版本目标、玩家反馈 | 版本 brief、优先级、里程碑 |
| 2. 需求拆解 | 产出可执行任务 | brief、规则库 | PRD、任务卡、验收项 |
| 3. 方案设计 | 形成技术和系统方案 | 任务卡、现有代码 | 设计文档、接口定义、目录调整 |
| 4. 代码实现 | 自动编写和修改代码 | 设计文档、任务卡 | 代码、配置、脚本、测试 |
| 5. 资源生成 | 生成 NPC、文本、图像、场景草案 | 世界规则、投票结果、模板 | 资源包、内容包 |
| 6. 自动验证 | 运行测试和试玩 | 代码、资源、构建环境 | 测试报告、失败日志 |
| 7. 迭代修复 | 根据失败结果自动修复 | 报错、日志、测试报告 | 修复补丁 |
| 8. 构建发布 | 输出可部署版本 | 通过的分支 | 构建产物、版本包、回滚包 |
| 9. 数据回流 | 用线上数据驱动下一轮开发 | 埋点、反馈、异常 | 新一轮需求输入 |

这个九段式链路就是整个项目的研发主循环。

## AI 团队编排

不要让一个 AI 从头包到尾。更稳妥的做法是把 AI 组织成一组固定职责的代理，每个代理只负责自己那部分工作。

### 建议的代理角色

| 代理 | 职责 |
|------|------|
| `Product Agent` | 读取目标、玩家反馈和路线图，输出版本需求和优先级。 |
| `System Designer Agent` | 设计玩法系统、模块边界、数据结构和接口约束。 |
| `Gameplay Agent` | 编写 Godot 场景、角色控制、战斗、交互和任务逻辑。 |
| `World Agent` | 生成 NPC、区域、事件、任务和世界描述配置。 |
| `Backend Agent` | 编写投票服务、生成服务、审核服务和运营后台接口。 |
| `QA Agent` | 编写和执行自动化测试、试玩脚本、回归检查。 |
| `Build Agent` | 打包客户端、服务端、内容包，管理版本和发布。 |
| `Ops Agent` | 读取监控和线上数据，归纳问题并形成下一轮输入。 |

### 编排方式

建议由一个 `Orchestrator` 统一调度所有代理。它不是再写业务代码，而是负责：

1. 判断一个任务该由谁处理。
2. 把上游产物转成下游输入。
3. 记录任务状态和失败原因。
4. 控制重试次数和回滚策略。
5. 在门禁不通过时阻断继续推进。

这个调度层可以直接用 Python 实现，不需要很重的智能体框架，核心是稳定和可观测。

## 仓库与目录设计

为了让 AI 能长期维护仓库，建议一开始就把项目拆成单仓或轻量 mono-repo，而不是把内容分散在很多难以同步的地方。

```text

├── docs/
│   ├── 00-governance/
│   ├── 10-requirements/
│   ├── 20-specs/
│   ├── 30-api/
│   ├── 40-dev-loop/
│   └── 50-research/
├── game/
│   ├── scenes/
│   ├── scripts/
│   ├── ui/
│   ├── config/
│   └── tests/
├── services/

├── content/

│   ├── npc-templates/
```

这个结构的目的不是好看，而是让 AI 在任何时刻都能快速定位“需求在哪、规则在哪、玩法代码在哪、服务代码在哪、测试在哪”。

## 标准研发流水线

### 阶段一：版本目标生成

输入是长期愿景、当前版本状态、玩家投票结果、线上数据和问题列表。`Product Agent` 根据这些信息生成本次版本的 `version_brief.md`，至少包含：

1. 本期目标
2. 不做什么
3. 核心指标
4. 关键风险
5. 验收口径

### 阶段二：需求自动拆解

`Product Agent` 和 `System Designer Agent` 联合把 `version_brief.md` 拆成任务卡。每张任务卡必须有：

1. 背景
2. 范围
3. 约束
4. 输入文件
5. 输出文件
6. 测试方法
7. 通过标准

任务卡样式建议固定成 Markdown 模板，因为这是后续所有代理的统一输入。

### 阶段三：技术方案与改动计划

`System Designer Agent` 根据任务卡输出：

1. 改动模块清单
2. 数据结构变化
3. 场景和资源变更点
4. 接口增量
5. 风险说明

如果方案涉及跨模块改动，先写 `design-note.md`，通过校验后再让编码代理动手。

### 阶段四：AI 自动编码

`Gameplay Agent`、`Backend Agent` 和 `World Agent` 分别处理自己的改动范围。编码时要遵守两个规则：

1. 一次只处理一张任务卡或一个原子子任务。
2. 提交代码时必须同时补测试，不允许“先实现后补”。

这里推荐把编码流程做成：

1. 读取任务卡
2. 分析相关文件
3. 生成 patch
4. 运行局部测试
5. 写变更说明
6. 提交到候选分支

### 阶段五：自动资源与内容生成

这一阶段是游戏项目和普通软件项目最大的区别。除了代码，AI 还要负责生成游戏内容，但内容不能裸生成，必须通过“规则模板 + 参数填充”的方式落地。

建议内容流水线如下：

1. `World Agent` 读取世界规则和投票结果。
2. 生成结构化中间稿，如 NPC JSON、任务 JSON、区域配置 YAML。
3. 规则引擎检查世界观、数值和安全约束。
4. 通过后再由 AI 生成文本润色、对话和场景描述。
5. 形成内容包并进入测试环境。

也就是说，AI 先生成结构，再生成表现；先过规则，再进世界。

### 阶段六：自动测试和试玩

这是闭环能否成立的核心。建议建立三层验证：

| 层级 | 验证方式 |
|------|----------|
| 代码测试 | 单元测试、接口测试、静态检查、格式检查 |
| 引擎测试 | 场景加载测试、节点引用检查、存档读写测试 |
| 玩法测试 | 自动移动脚本、任务完成脚本、战斗脚本、路径卡死检测 |

对于 Godot，可以专门准备一套 headless 测试入口，让 `QA Agent` 自动执行以下动作：

1. 加载主场景
2. 进入指定区域
3. 触发任务
4. 完成一次基础战斗
5. 执行一次投票流程
6. 验证更新后内容是否能正常加载

如果这些都能自动跑通，AI 才有可能连续迭代而不把游戏搞坏。

### 阶段七：失败自动修复

任何一次失败都不能只把日志丢出来结束，而要进入自动修复流程：

1. 收集失败日志、栈追踪、截图和测试步骤。
2. 由 `QA Agent` 生成失败摘要。
3. 由对应编码代理尝试修复。
4. 修复后只重跑相关测试。
5. 连续失败超过阈值则升级为高风险任务。

这个机制的关键是让 AI 修复时拿到的是结构化失败上下文，而不是一堆原始日志。

### 阶段八：构建与发布

当所有门禁通过后，`Build Agent` 执行：

1. 客户端构建
2. 服务端镜像构建
3. 内容包打包
4. 版本元数据写入
5. 回滚包生成

上线时建议分成三步：

1. 先发测试环境
2. 再发灰度环境
3. 最后全量

如果你真的希望做到“无人值守上线”，那么至少要在灰度阶段设置自动止损条件，例如崩溃率、任务失败率、异常奖励率超过阈值时自动停止全量发布。

### 阶段九：线上数据回流

研发闭环只有在“上线后还能反哺下一轮开发”时才算完整。建议把以下数据直接作为下一轮 `Product Agent` 的输入：

1. 区域到达率
2. 任务完成率
3. 玩家投票参与率
4. 新内容停留时长
5. 异常退出率
6. AI 生成内容被驳回率
7. 高频反馈主题

这样下一轮版本目标就不是凭感觉生成，而是从真实数据里提炼。

## 可落地的工程约束

要让整个闭环真的能跑，项目必须接受一些工程约束。

### 1. 代码规范必须机器可判定

不要依赖“资深工程师一眼就知道哪段写得不好”。所有规范都要落成规则，比如：

1. 命名规范
2. 文件层级规范
3. 依赖引用规范
4. 场景节点命名规范
5. 配置字段完整性规范

### 2. 所有改动必须绑定任务卡

AI 不允许“顺手改点别的”。每次改动都必须关联任务编号，否则上下文会越来越乱，最后没有人能说清这段代码为什么存在。

### 3. 资源生成必须走模板

贴图、图标、对话、任务描述、NPC 设定、区域事件，都要先有模板和边界。没有模板，AI 内容会越来越像随机拼接。

### 4. 线上发布必须可回滚

如果某次生成内容把某个区域任务链打断，或者把某种奖励刷爆，没有回滚就等于把整个闭环交给运气。

## 推荐的最小可运行版本

如果你现在就要启动，建议不要一开始就让 AI 接管整个大型开放世界，而是先做一个最小可运行闭环，目标是 6 到 10 周内跑通以下流程：

### 第一阶段

完成这几个部分：

1. `Godot 4` 基础项目骨架
2. 一个核心区域
3. 基础移动、交互、战斗和任务系统
4. 一个投票服务
5. 一个内容生成服务
6. 一个规则审核服务
7. 一套自动测试和构建流水线

### 第一阶段验收

只要能完成下面这条链路，就说明闭环已经成立：

1. 玩家进入区域
2. 完成任务并触发一次世界状态变化
3. 参与一次投票
4. 服务端生成新的 NPC 和支线任务
5. 规则引擎审核通过
6. 内容包上线到测试服
7. 客户端正常加载并可继续游玩

如果这条链路跑通，再逐步增加地图规模、任务深度、区域数量和自动生成范围。

## 实施分期

### P0：基础设施期

目标是让 AI 能稳定写、测、改、发。重点建设：

1. 仓库结构
2. 任务卡模板
3. 编码规范
4. 测试框架
5. CI/CD
6. 日志与审计

### P1：最小玩法闭环期

目标是跑通单区域、单任务链、单次投票、单次内容更新的最小闭环。

### P2：多代理协同期

目标是把玩法代理、后端代理、内容代理、QA 代理和发布代理串起来，形成真正自动化研发。

### P3：线上运营闭环期

目标是让线上数据自动回流，驱动下一轮需求和内容更新，形成持续迭代系统。

## 主要风险

| 风险 | 具体表现 | 对策 |
|------|----------|------|
| 上下文失控 | AI 改动越来越分散，代码风格逐渐崩坏 | 强制任务卡、目录约束和变更边界 |
| 引擎资产难维护 | 场景、节点、资源引用频繁失效 | 选文本化引擎，建立节点与场景校验脚本 |
| 内容质量下滑 | 任务、NPC、区域越来越模板化 | 模板管理、重复度检测、质量评分 |
| 测试不足 | AI 写了很多功能但没人知道是否可玩 | 自动试玩脚本和最小路径回归测试 |
| 发布风险 | 自动生成内容直接进线上导致事故 | 灰度发布、规则引擎、回滚包 |
| 组织误判 | 以为“有大模型”就等于“能自动做完游戏” | 先做闭环，再做规模，不先追求内容量 |

## 最终建议

如果你的目标是“完全由 AI coding 实现整个游戏开发闭环”，最可落地的路径不是一开始追求最大规模，而是先把研发系统本身做成 AI 能执行的形状。  
先让 AI 稳定完成一个小型开放区域的完整闭环，再逐步扩大到多区域、多任务链、多代理协同和线上运营回流。

一句话概括这套方案：**先建设 AI 可执行的工厂，再让 AI 去生产游戏。**
