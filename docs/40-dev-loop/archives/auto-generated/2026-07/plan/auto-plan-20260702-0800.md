## 任务目标与背景

vote-service、world-service 和 content-service 已完整实现并通过验证，具备投票链路、区域管理和内容包管理能力。但 MVP 的内容生成链路还缺少核心环节——generation-service 负责组织 AI 生成请求、模板加载和结果落库，是连接投票结果与内容产出的关键桥梁。

根据 `backend-data-spec.md` 定义，`generation_requests` 表记录异步生成任务，`generated_objects` 表存储 AI 生成的内容对象供后续审核。API 规范中已定义运营审核接口（`POST /api/v1/ops/review/{object_id}/approve`），但生成请求的创建、查询和状态管理尚未实现。

**本次目标**：初始化 generation-service 服务骨架，实现生成请求（generation_requests）和生成对象（generated_objects）数据模型、运营管理接口（创建生成请求、查询请求状态、查询生成对象）、JWT 认证、统一响应 envelope、审计日志持久化，遵循 vote-service、world-service 和 content-service 已验证的架构模式。

## 具体执行步骤

### 步骤 1：创建服务骨架与配置

- 复制 content-service 目录结构作为 generation-service 基础
- 修改服务名称、配置前缀（GENERATION_）、数据库连接
- 更新 pyproject.toml 项目元信息
- 创建 `.env.example` 配置模板
- 更新 README.md

### 步骤 2：定义领域模型（GenerationRequest + GeneratedObject + AuditLog）

- 在 `app/domain/models.py` 中实现：
  - `GenerationRequest` 模型：request_id, vote_cycle_id, source_candidate_id, template_id, input_payload_jsonb, status, retry_count, max_retries, error_message, trace_id, created_at, updated_at
  - `GeneratedObject` 模型：object_id, request_id, object_type, schema_version, object_payload_jsonb, quality_score, status, created_at, updated_at
  - `AuditLog` 模型（复用已有模式）
- 生成请求状态枚举：pending / processing / succeeded / failed_retryable / failed_permanent
- 生成对象状态枚举：pending_review / approved / rejected / needs_revision
- CHECK 约束、索引（status, trace_id, request_id, object_type）
- 遵循 `11-database.md` 规范（UUID 主键、审计字段、JSONB）
- 外键：generated_objects.request_id → generation_requests.request_id ON DELETE CASCADE

### 步骤 3：实现数据访问层（Repository）

- 创建 `GenerationRepository` 类
- 方法：
  - `create_request(...)` - 创建生成请求（pending 状态）
  - `get_request_by_id(request_id)` - 获取请求详情
  - `list_requests(status, limit, offset)` - 运营查询请求列表
  - `update_request_status(request_id, status, error_message)` - 更新请求状态
  - `increment_retry(request_id)` - 增加重试次数
  - `create_generated_object(...)` - 创建生成对象
  - `get_object_by_id(object_id)` - 获取生成对象详情
  - `list_objects_by_request_id(request_id)` - 按请求查询对象列表
  - `update_object_status(object_id, status)` - 更新对象审核状态
  - `list_objects(status, object_type, limit, offset)` - 运营查询对象列表
- 创建 `AuditRepository` 类（复用已有模式）

### 步骤 4：实现 Pydantic Schemas

- 通用 envelope 响应（EnvelopeResponse、PaginatedMeta、ErrorResponse）
- 生成请求相关：
  - `GenerationRequestResponse` - 生成请求响应模型
  - `GenerationRequestListResponse` - 生成请求列表响应
  - `CreateGenerationRequestRequest` - 创建生成请求请求
  - `UpdateGenerationRequestRequest` - 更新状态请求
  - `GenerationRequestStatus` 枚举
- 生成对象相关：

  - `GeneratedObjectListResponse` - 生成对象列表响应

### 步骤 5：实现 API 路由

- 健康检查：`GET /api/v1/health`
- 运营接口（JWT + ops scope）：
  - `POST /api/v1/ops/generation/requests` - 创建生成请求
  - `GET /api/v1/ops/generation/requests` - 查询生成请求列表（分页）
  - `GET /api/v1/ops/generation/requests/{request_id}` - 获取生成请求详情
  - `POST /api/v1/ops/generation/requests/{request_id}/status` - 更新生成请求状态
  - `GET /api/v1/ops/generation/objects` - 查询生成对象列表（分页）
  - `GET /api/v1/ops/generation/objects/{object_id}` - 获取生成对象详情
  - `POST /api/v1/ops/generation/objects/{object_id}/status` - 更新生成对象状态（审核）

### 步骤 6：集成 JWT 认证与权限

- 生成请求管理需要 ops 角色权限
- 生成对象审核需要 `review:approve` scope
- 所有接口需 Bearer Token 认证

### 步骤 7：集成审计日志

### 步骤 8：实现状态机校验

- 生成请求状态机：pending → processing → succeeded / failed_retryable → pending（重试） / failed_permanent
- 生成对象状态机：pending_review → approved / rejected / needs_revision
- 非法状态迁移返回 409 + INVALID_GENERATION_STATUS / INVALID_OBJECT_STATUS
