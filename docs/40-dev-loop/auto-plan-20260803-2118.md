## 二、任务目标与背景

### 背景

`docs/00-governance/project-status.md` 第 82 行记录：

> **M4 WP4 发布自动化与周更节奏（未开始，按序）**：自动审核通过内容自动进入发布队列（审核→打包→发布串联）。

自 2026-07-27 起研发闭环因 Docker / PostgreSQL / Redis / workers 运行时不可用进入「节流 / 优雅结束」常态，连续多轮无新代码合并。本轮经代码级排查确认：**WP4 首个条目「审核 → 打包 → 发布串联」实为纯代码接线缺口，其单元测试全部基于 SQLite 内存库 + Celery eager 模式 + Mock HTTP 客户端，无需任何真实运行时**，因此可在当前环境下完整实施，不再受硬阻塞约束。

该缺口早在 `docs/40-dev-loop/auto-execution-summary-20260723-0443.md` 第 38 行已被登记为 W1，一直未销项。

### 现状诊断（代码级）

链路两端均已就位，中间接线断开两处：

1. **review 侧不发事件**：`services/review/app/api/routes.py::auto_review`（第 599 行起）在 `auto_review_engine.evaluate()` 判定为 `approved` 后，仅落库 + 记录指标 + 写审计日志，**未发布任何事件**即返回（第 666 行）。对比手工批量通过路径 `approve_review_object`（第 372 行）已在第 445 行发布 `review.batch.completed`，auto 路径完全缺失。
2. **workers 侧无消费者触发发布**：`workers/tasks/content_release.py::release_content_package`（第 29 行）已实现完整发布逻辑，但仅能由 `promote_to_full_release` 与 ops 手工端点触发，**没有任何事件处理器会调用它**。

发布队列本身已存在：`services/content/app/domain/models.py::ReleaseRecord`（第 106-145 行，`status` 支持 `queued/running/completed/failed`）与 `ContentPackage.status`（第 97 行）。

### 目标

打通「自动审核通过 → 发布队列」的事件驱动串联，使自动审核通过的内容包能自动进入灰度发布流程，同时保留高风险内容的人工确认闸口。

## 五、设计决策

1. **为何新增独立事件类型而非复用 `review.batch.completed`**：`review.batch.completed` 语义为「一批人工审核完成」，其 payload 无 `content_package_id`；且现有 `handle_review_batch_completed` 消费后触发的是 `run_full_content_review`（复审）而非发布，语义不同。新增 `review.auto.approved` 保持事件语义单一。
2. **默认 `release_mode="gray"`**：尽管管理决策已明确跳过灰度阶段，但「无人工介入的自动发布」直接全量上线风险过高，故自动链路默认走灰度，全量发布仍需 `promote_to_full_release` 人工推进。事件 payload 允许显式覆盖。
3. **风险闸口**：`docs/20-specs/content-generation-spec.md` 要求高危节点留人工确认，故处理器对 `risk_level` 非 `low` 的事件仅记录日志、不入队。
4. **`content_package_id` 设为可选**：既有 `/review/auto` 调用方未携带该字段，设为必填会造成破坏性变更；缺失时降级为「仅审核不发布」并记日志。
