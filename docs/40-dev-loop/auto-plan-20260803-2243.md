## 二、任务目标与背景

本轮销项上一轮（`auto-20260803-2118`）执行摘要 §九 明确登记的**两个纯代码残留缺口**，二者均已确认**不依赖真实运行时**，可离线实施与验证。

### 缺口 1（主任务，P0）：`handle_review_batch_completed` 恒为死代码

`workers/events/handlers.py::handle_review_batch_completed` 的守卫条件为：

```python
content_package_id = payload.get("content_package_id")
approved_count = payload.get("approved_count", 0)
if content_package_id and approved_count > 0:
    run_full_content_review.delay(...)
```

但事件生产侧 `services/review/app/core/event_publisher.py::publish_review_batch_completed`
的 payload **从未写入 `content_package_id`** 键：

```python
{"batch_id", "request_id", "approved_count", "rejected_count",
 "needs_revision_count", "completed_at"}
```

因此 `content_package_id` 恒为 `None`，守卫恒为假，`run_full_content_review`
**永远不会被人工审核批量通过路径触发** —— 「人工审核通过 → 全量复审」这一链路实际断开。

附带口径缺陷：`services/review/app/api/routes.py` 两处调用均硬编码 `request_id=""`，
消费侧无法回溯来源生成请求。

### 缺口 2（次任务，P1）：`test_event_bus.py` 强依赖真实 Redis

5 个用例直连 `localhost:6379`，导致 workers 套件离线时固定 5 failed。
该失败已跨多轮被反复确认为「环境型既有失败」，掩盖真实回归信号。
`EventPublisher.__init__` 已支持注入 `event_bus`，具备低侵入 mock 化条件。

### 顺带修复（同类缺陷复发）

上一轮修复了 `handle_vote_result_finalized` 中「标准库 `logging.Logger`
误用 structlog 风格关键字参数」的运行期 `TypeError` 隐患，但**同文件
`handle_player_event` 中仍存在两处同类误用**（`logger.info` 与 `logger.error`
各一处），上一轮遗漏。该处理器一旦被真实玩家事件触发即崩溃，且
`except` 分支中的 `logger.error` 会在异常处理中再次抛出，掩盖原始异常。
