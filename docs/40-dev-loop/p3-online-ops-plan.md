## 阶段目标

### 核心目标

将游戏从"一次性内容消费"转变为"长期共同塑造的世界体验"，实现：

1. **数据自动回流**：玩家行为、投票结果、内容消费数据自动采集并存储
2. **洞察自动提取**：从回流数据中自动提取玩家偏好和行为模式
3. **需求自动生成**：基于洞察自动生成下一轮内容和玩法需求
4. **闭环持续演进**：形成"线上运营 → 数据回流 → 需求生成 → 内容生产 → 上线"的完整闭环

### 范围定义

| 范围 | 包含 | 排除 |
|------|------|------|
| 数据采集 | 玩家行为、投票结果、内容消费、任务完成 | 实时语音聊天、玩家私人消息 |
| 数据分析 | 偏好分析、趋势识别、异常检测、价值评估 | 实时推荐系统、深度学习模型训练 |
| 需求生成 | 内容扩展建议、玩法调整建议、世界演进建议 | 核心玩法规则变更、经济系统重构 |
| 闭环执行 | 数据驱动的内容生成、投票主题生成 | 自动化发布决策（需人工复核） |

## 核心闭环设计

### 闭环架构

```
线上运营 → 数据采集 → 数据存储 → 数据分析 → 洞察提取 → 需求生成 → 内容生产 → 审核发布 → 上线 → 线上运营
     ↑                                                                                              │
     └──────────────────────────────────────────────────────────────────────────────────────────────┘
```

### 闭环环节说明

| 环节 | 职责 | 输入 | 输出 | 关键指标 |
|------|------|------|------|----------|
| 数据采集 | 从客户端和服务端采集玩家行为数据 | 玩家操作、投票记录、任务状态、区域访问 | 结构化事件日志 | 采集覆盖率、数据完整性 |
| 数据存储 | 存储回流数据，支持分析查询 | 事件日志、聚合数据 | 数据仓库 | 存储效率、查询性能 |
| 数据分析 | 清洗数据并进行统计分析 | 原始数据 | 分析报告、趋势数据 | 分析时效性、准确率 |
| 洞察提取 | 从分析结果中提取有价值的洞察 | 分析报告 | 洞察条目 | 洞察质量、业务价值 |
| 需求生成 | 将洞察转化为具体需求 | 洞察条目 | 需求包 | 需求质量、可执行性 |
| 内容生产 | 根据需求生成游戏内容 | 需求包 | 内容包 | 生成质量、审核通过率 |
| 审核发布 | 审核内容并发布上线 | 内容包 | 上线内容 | 审核速度、发布成功率 |

## 关键技术组件

### 1. 数据采集层

#### 1.1 客户端行为采集

- **事件类型**：
  - `player.enter_region` - 玩家进入区域
  - `player.leave_region` - 玩家离开区域
  - `player.complete_quest` - 玩家完成任务
  - `player.interact_npc` - 玩家与 NPC 交互
  - `player.vote_submit` - 玩家提交投票
  - `player.view_content` - 玩家查看内容
  - `player.spend_resource` - 玩家消耗资源

- **采集机制**：
  - 客户端定时批量上报（默认 30 秒间隔）
  - 关键事件实时上报（投票、任务完成）
  - 事件去重与幂等处理

#### 1.2 服务端数据采集

- **数据源**：
  - 投票服务：投票记录、投票结果、投票趋势
  - 内容服务：内容包发布、回滚、灰度可见性
  - 玩家服务：玩家注册、成长、声望变化
  - 世界服务：区域解锁、阵营声望变化

- **采集机制**：
  - 现有审计日志扩展为分析日志
  - 业务指标作为聚合数据来源
  - 事件总线事件作为实时数据流

### 2. 数据存储层

#### 2.1 事件日志存储

- **存储方案**：PostgreSQL JSONB（短期）+ 数据仓库（长期）
- **表结构**：`player_events`（事件流水表）
- **分区策略**：按月分区，支持快速查询和归档

#### 2.2 聚合数据存储

- **存储方案**：PostgreSQL 关系表
- **聚合维度**：按玩家、区域、任务、投票周期聚合
- **更新策略**：定时批处理 + 实时增量

### 3. 数据分析层

#### 3.1 数据清洗

- 去重：基于事件 ID 和时间窗口
- 过滤：无效事件、测试数据、异常值
- 标准化：统一时间格式、区域编码、玩家标识

#### 3.2 统计分析

- 基础指标：活跃玩家数、在线时长、任务完成率
- 趋势分析：投票倾向变化、区域热度变化、任务难度分布
- 关联分析：投票结果与内容消费的相关性

#### 3.3 异常检测

- 异常投票模式检测
- 内容消费异常检测
- 玩家行为异常检测

### 4. 洞察提取层

#### 4.1 洞察分类

| 类别 | 示例 | 优先级 |
|------|------|--------|
| 内容偏好 | 玩家更喜欢探索型任务 | P1 |
| 区域热度 | 灰谷废墟访问量远超预期 | P1 |
| 投票倾向 | 玩家倾向选择和平发展选项 | P2 |
| 难度反馈 | 某任务难度偏高导致完成率低 | P1 |
| 内容缺口 | 某区域缺少支线任务 | P2 |

#### 4.2 洞察质量评估

- **置信度**：数据支撑强度（高/中/低）
- **影响力**：对游戏体验的影响程度（高/中/低）
- **新颖度**：与现有认知的差异程度（高/中/低）
- **可行性**：实现难度和资源需求（高/中/低）

### 5. 需求生成层

#### 5.1 需求生成流程

1. 接收洞察条目（含置信度、影响力评估）
2. 匹配现有世界骨架和内容约束
3. 生成需求包（含目标、范围、验收标准）
4. 评估需求优先级（基于影响力和可行性）
5. 输出排序后的需求队列

#### 5.2 需求包格式

需求包遵循 `docs/40-dev-loop/auto-plan.md` 模板格式，包含：
- task_id：需求标识
- 目标与背景
- 具体执行步骤
- 涉及的文件与目录
- 验收标准与 checklist

### 6. 闭环执行层

#### 6.1 需求驱动的内容生成

- 根据需求包自动调用 World Agent 生成内容
- 生成内容进入审核流程
- 审核通过后进入发布流程

#### 6.2 需求驱动的投票主题生成

- 根据玩家偏好洞察生成投票候选项
- 运营人员审核后发布投票
- 投票结果进入下一轮闭环

## 数据回流机制设计

### 数据回流架构

```
客户端 ──────┐
            │ 事件上报 API
            ↓
      gateway-service ──────────────────────┐
            │                               │
            ↓                               │ 事件转发
      事件总线 ──────────────┐              │
            │               │              │
            ↓               ↓              │
    实时处理              离线处理          │
            │               │              │
            ↓               ↓              │
    实时指标            数据仓库            │
            │               │              │
            └───────────────┴──────────────┘
                          │
                          ↓
                    分析引擎 ──────→ 洞察提取 ──────→ 需求生成
```

### 事件格式规范

所有回流事件必须遵循统一格式：

```json
{
  "event_id": "evt_20260709_abc123",
  "event_type": "player.complete_quest",
  "player_id": "player_xxx",
  "region_id": "region_wasteland_01",
  "timestamp": "2026-07-09T13:00:00Z",
  "payload": {
    "quest_id": "quest_rescue_01",
    "duration_seconds": 1200,
    "rewards_collected": ["gold_100", "exp_500"]
  },
  "trace_id": "trace_xxx",
  "schema_version": 1
}
```

### 数据保留策略

| 数据类型 | 保留期限 | 存储位置 |
|----------|----------|----------|
| 原始事件日志 | 90 天 | PostgreSQL |
| 聚合数据 | 永久 | PostgreSQL |
| 分析报告 | 永久 | PostgreSQL |
| 洞察记录 | 永久 | PostgreSQL |

## 数据驱动需求流程

### 流程架构

```
数据采集 → 数据存储 → 数据清洗 → 统计分析 → 洞察提取 → 需求生成 → 需求审核 → 需求执行
```

### 各环节详细设计

#### 1. 数据采集（持续运行）

- **频率**：实时（关键事件）+ 批量（每 30 秒）
- **可靠性**：事件去重、重试机制、断点续传

#### 2. 数据存储（持续运行）

- **写入**：流式写入 + 批量写入
- **查询**：支持按玩家、时间、事件类型多维查询

#### 3. 数据清洗（每日执行）

- **时间**：每日凌晨 2:00
- **任务**：去重、过滤、标准化
- **输出**：清洗后的结构化数据

#### 4. 统计分析（每日执行）

- **时间**：每日凌晨 3:00
- **任务**：计算基础指标、趋势分析、关联分析
- **输出**：分析报告

#### 5. 洞察提取（每周执行）

- **时间**：每周一凌晨 4:00
- **任务**：从分析报告中提取洞察
- **输出**：洞察条目列表（含质量评估）

#### 6. 需求生成（每周执行）

- **时间**：每周一凌晨 5:00
- **任务**：将洞察转化为需求包
- **输出**：需求包队列（按优先级排序）

#### 7. 需求审核（运营介入）

- **方式**：运营人员审核需求包
- **输出**：审核通过/拒绝的需求包

#### 8. 需求执行（自动执行）

- **方式**：Orchestrator 自动调度执行
- **输出**：完成的任务成果

## 关键接口设计

### 数据采集接口

#### POST /api/v1/events/batch

**功能**：批量上报客户端事件

**请求体**：
```json
{
  "events": [
    {
      "event_type": "player.enter_region",
      "player_id": "player_xxx",
      "region_id": "region_wasteland_01",
      "timestamp": "2026-07-09T13:00:00Z",
      "payload": {},
      "trace_id": "trace_xxx"
    }
  ]
}
```

**响应**：统一 envelope 格式

### 数据分析接口

#### GET /api/v1/analytics/player-metrics

**功能**：获取玩家行为指标

**查询参数**：
- `player_id`：玩家 ID（可选）
- `region_id`：区域 ID（可选）
- `start_date`：开始日期
- `end_date`：结束日期

**响应**：
```json
{
  "request_id": "req_xxx",
  "data": {
    "total_playtime": 3600,
    "regions_visited": 5,
    "quests_completed": 10,
    "votes_submitted": 3
  },
  "meta": {},
  "trace_id": "trace_xxx"
}
```

#### GET /api/v1/analytics/trends

**功能**：获取趋势分析数据

**查询参数**：
- `metric_type`：指标类型（region_visits / quest_completion / vote_preference）
- `time_range`：时间范围（7d / 30d / 90d）

**响应**：
```json
{
  "request_id": "req_xxx",
  "data": {
    "metric_type": "region_visits",
    "time_range": "7d",
    "trends": [
      {"date": "2026-07-02", "value": 100},
      {"date": "2026-07-03", "value": 120}
    ]
  },
  "meta": {},
  "trace_id": "trace_xxx"
}
```

### 洞察与需求接口

#### GET /api/v1/insights

**功能**：获取洞察列表

**查询参数**：
- `page`：页码
- `per_page`：每页数量
- `min_confidence`：最低置信度（high/medium/low）
- `min_impact`：最低影响力（high/medium/low）

**响应**：
```json
{
  "request_id": "req_xxx",
  "data": [
    {
      "insight_id": "insight_xxx",
      "category": "content_preference",
      "summary": "玩家更喜欢探索型任务",
      "confidence": "high",
      "impact": "medium",
      "discovered_at": "2026-07-09T04:00:00Z"
    }
  ],
  "meta": {
    "total": 10,
    "page": 1,
    "per_page": 20
  },
  "trace_id": "trace_xxx"
}
```

#### POST /api/v1/ops/insights/{insight_id}/generate-requirement

**功能**：基于洞察生成需求包

**响应**：
```json
{
  "request_id": "req_xxx",
  "data": {
    "requirement_id": "auto-xxx",
    "insight_id": "insight_xxx",
    "status": "pending_review",
    "generated_at": "2026-07-09T05:00:00Z"
  },
  "meta": {},
  "trace_id": "trace_xxx"
}
```

| 风险 | 概率 | 影响 | 应对策略 |

## 与其他阶段的关系

```
P0（基础设施）→ P1（最小玩法闭环）→ P2（多代理协同）→ P3（线上运营闭环）
     ↑                                                      │
     └──────────────────────────────────────────────────────┘
```

- P3 依赖 P1/P2 的所有基础设施和代理能力
- P3 的数据回流为 P2 的代理提供输入
- P3 的需求生成为 P1 的玩法闭环提供新内容
- P3 完成后形成完整的"运营 → 数据 → 需求 → 生产 → 运营"闭环

## 后续阶段展望

P3 完成后，项目将进入持续运营阶段：
- 线上数据持续回流
- 需求自动生成和优先级排序
- 内容自动生成和审核
- 运营人员专注于质量把控和战略决策
