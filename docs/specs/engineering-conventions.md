# 工程协作详细规范

## 目标

本规范统一仓库结构、命名方式、配置管理、版本策略和协作约束，减少 Agent 与人类在文件组织、环境差异和发布操作上的不一致。

## 仓库结构规范

建议主仓库采用以下目录：

```text
game-project/
├── docs/
│   ├── requirements/
│   ├── dev-loop/
│   ├── research/
│   └── specs/
├── game/
│   ├── project.godot
│   ├── scenes/
│   ├── scripts/
│   ├── data/
│   ├── assets/
│   └── tests/
├── services/
│   ├── gateway/
│   ├── player/
│   ├── world/
│   ├── vote/
│   ├── generation/
│   ├── review/
│   ├── content/
│   └── ops/
├── workers/
├── tools/
├── infra/
├── telemetry/
└── .github/
```

## 目录职责

- `game/`
  - Godot 客户端工程
- `services/`
  - Web API 与后台服务
- `workers/`
  - Celery 或其他异步任务入口
- `tools/`
  - 离线脚本、校验器、打包工具
- `infra/`
  - Docker、Compose、部署配置
- `telemetry/`
  - 指标、日志、告警定义

## 命名规范

### 通用命名

- 目录：小写短横线或小写英文单词
- 文件：优先小写短横线
- ID：使用稳定前缀

### 推荐前缀

- `region_`
- `chapter_`
- `npc_`
- `quest_`
- `event_`
- `pkg_`
- `gate_`
- `rule_`

### 版本命名

- 内容包：`pkg_<chapter>_<region>_<yyyymmdd>_<seq>`
- 模板版本：`tpl_<domain>_v<major>.<minor>`
- 规则版本：`rule_<domain>_v<major>.<minor>`

## Godot 侧规范

### 场景规范

- 每个核心玩法实体应有独立场景
- 场景文件与主脚本文件同名
- 场景目录按领域划分，例如：
  - `scenes/player/`
  - `scenes/npc/`
  - `scenes/world/`
  - `scenes/ui/`

### 脚本规范

- 默认使用 typed GDScript
- 单文件尽量只承载一个主要职责
- 复杂配置放入 `data/`，不要硬编码在场景脚本里
- 运行时依赖优先通过配置注入，不直接写死路径

### 数据规范

- 客户端静态数据统一放在 `game/data/`
- 生成内容与常量模板分目录存放
- 所有数据文件必须带 `schema_version`

## Python 服务端规范

### 项目结构

每个服务建议至少包含：

- `app/api/`
- `app/domain/`
- `app/repositories/`
- `app/schemas/`
- `app/tasks/`
- `tests/`

### 代码约束

- 接口输入输出必须定义 schema
- 数据访问不得在路由层直接拼 SQL
- 长任务不得在 Web 进程同步执行
- 配置统一来自环境变量与配置文件

## 配置管理规范

### 配置分层

- `default`
  - 默认安全配置
- `local`
  - 本地开发配置
- `test`
  - 自动测试配置
- `staging`
  - 预发布配置
- `prod`
  - 生产配置

### 配置要求

- 禁止把密钥写入仓库
- 所有关键开关必须可在配置层关闭
- 发布、灰度、回滚阈值必须配置化

## 分支与版本规范

### 分支

- `main`
  - 稳定可发布
- `develop`
  - 集成开发
- `feature/<name>`
  - 功能分支
- `fix/<name>`
  - 修复分支

### 版本

- 服务端使用语义化版本
- 内容包使用独立包版本
- 客户端版本与内容版本必须可映射

## Git 提交规范

### 提交格式

- 提交信息统一使用：
  - `<type>(<scope>): <summary>`
- 其中：
  - `type` 表示变更类型
  - `scope` 表示影响范围，可选但推荐保留
  - `summary` 使用简短祈使句，说明本次提交做了什么

### 推荐类型

- `docs`
  - 文档新增、重组、修订
- `feat`
  - 新功能
- `fix`
  - 缺陷修复
- `refactor`
  - 不改变行为的结构调整
- `test`
  - 测试新增或修订
- `chore`
  - 构建、脚本、依赖或杂项维护

### Scope 约定

- 文档相关提交推荐使用以下 scope：
  - `docs`
  - `specs`
  - `requirements`
  - `dev-loop`
  - `skills`
  - `api`
- 工程相关提交按实际模块命名，例如：
  - `gateway`
  - `vote`
  - `content`
  - `game`

### 提交要求

- 一次提交只表达一个清晰主题，避免把无关变更混在同一次提交里。
- `summary` 控制在一行内，优先写“新增 / 补充 / 调整 / 修复”这类明确动作。
- `summary` 必须直接概括本次实际改动，不得照抄整段会话总结、任务描述或长篇计划说明。
- AI 提交时，提交信息应基于“这一次提交改了什么”生成，而不是基于“整个会话聊了什么”生成。
- 如果一次会话中包含多个独立改动，应拆成多次提交，并分别为每次提交写对应的简明摘要。
- 提交前应确认文档、代码、配置和相关说明已同步更新。
- 如本次提交依赖规范变更，优先先提交规范，再提交实现。

### 示例

- `docs(specs): 补充 git 提交规范`
- `docs(specs): 调整 AI 提交说明`
- `docs(api): 新增接口总览文档`
- `feat(vote): 增加投票提交接口`
- `fix(content): 修正内容包回滚状态判断`

## 测试规范

### 客户端

- 关键玩法流程必须有最小回归脚本
- 场景加载、任务触发、投票入口和结果展示必须覆盖

### 服务端

- 核心接口必须有单测与集成测试
- 投票结算、内容发布、回滚与权限检查必须覆盖

### 内容

- 每次上线内容必须经过一致性、数值、安全和重复度检查

## 发布规范

### 发布前

- 代码流水线全绿
- 内容流水线全绿
- 发布说明生成完成
- 回滚路径验证通过

### 发布中

- 优先灰度
- 观测关键指标至少一个窗口期
- 有异常立即暂停扩大范围

### 发布后

- 记录版本号、内容包号、操作人和结果
- 产出简短复盘摘要

## 变更审计规范

以下对象必须可追溯：

- 代码提交
- 配置修改
- 模板修改
- 规则修改
- 内容包上线
- 内容包回滚

每条记录至少包含：

- 操作者
- 时间
- 变更对象
- 变更原因
- 关联任务或 issue

## 完成定义

一个任务只有同时满足以下条件才算完成：

- 需求范围实现完毕
- 验收条件具备自动化信号
- 相关测试与门禁已更新
- 文档或配置同步更新
- 回滚路径清晰
